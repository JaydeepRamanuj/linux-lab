    reality: "A zombie has already exited. It's only an entry in the process table, waiting for its parent to read its exit status. Signals do nothing to it, because there's nothing left running. It goes away when the parent collects it, or when the parent exits and PID 1 collects it instead."

## The mental model

A **process** is a program that's running. The kernel gives each one a number, its **PID**, and keeps a record of it: which program it runs, which user it runs as, what memory it has, which files it has open, and what it's doing right now.

New processes come from old ones. A process calls `fork()` to make a copy of itself, and the copy calls `exec()` to replace itself with a different program. That's how your shell runs `ls`, as [What happens when you press Enter](/g/pressing-enter) shows. The copy is the **child**, the original is its **parent**, and the child's record keeps the parent's PID as its **PPID**.

Follow the parents up from any process and you always reach **PID 1**, the one process the kernel starts itself. So every process on the machine is part of one tree:

Every process is in one of a few **states**, shown in the `STAT` column of `ps`:

- **`R` running**, or ready to run as soon as a CPU core is free.
- **`S` sleeping**: waiting for something, such as a keypress, a network packet or a timer. This is the normal state. An idle server is `S`.
- **`D` uninterruptible sleep**: waiting inside the kernel for a disk or network filesystem, and not even signals can wake it. Short spells are normal. A process stuck in `D` for minutes usually means a hung drive or network mount.
- **`T` stopped**: paused, by Ctrl+Z or a debugger. It does nothing until it's continued.
- **`Z` zombie**: finished, but its parent hasn't collected its exit status yet.

Tools like `ps`, `top` and `pgrep` don't have any special access. They read the kernel's records, which appear as files under `/proc`. The [CPU and RAM scenario](/s/cpu-ram-hog) uses them to find what's slowing the machine down.

## Under the hood

**fork, then exec.** `fork()` creates a child that's an almost exact copy of the parent: the same memory (shared until either side writes to it), the same open files, the same environment and current folder. The only differences are the PID and the PPID. `exec()` then throws away the child's memory and loads a new program, but it keeps the PID, the open files and the environment. `bash -c 'echo $$; exec sh -c "echo \$\$"'` prints the same number twice: `exec` changed the program, not the process. That split is what lets a shell set up redirections in the child before the new program starts. The environment it passes on is explained in [How programs inherit their environment](/g/environment-variables).

**Orphans get a new parent.** If a parent dies first, the kernel hands its children to PID 1, or to the closest ancestor that has asked to be a **subreaper**. On an Ubuntu desktop that's usually your `systemd --user` manager. Under WSL it's a per-session `init` process. The orphan keeps running and doesn't notice. This is why stopping `npm run dev` can leave its `node` child behind holding a port: see [Ports and sockets](/g/ports-sockets).

**Zombies.** When a process exits, the kernel frees its memory and closes its files straight away, but it keeps the PID and the exit status until the parent calls `wait()`. Until then `ps` shows it as `Z` and `<defunct>`. Zombies use no CPU and no memory, only a slot in the table. They're a problem only when a buggy parent never collects them and they pile up in the thousands. Killing the parent fixes it: the zombies are adopted by PID 1, which collects them at once. [How exit status works](/g/exit-status) follows the status from `exit()` to `$?`.

**Threads.** A process can run several threads, which share its memory and files but are scheduled separately. Linux gives each thread an ID from the same number space as PIDs, and lists them under `/proc/<PID>/task/`. `ps` shows processes by default; `ps -L` or `top -H` shows threads. When `top` shows one process above 100% CPU, several of its threads are busy on different cores.

**The kernel's own threads.** On a normal install, PID 2 is `kthreadd`, the parent of the kernel's internal worker threads. They appear in `ps` in square brackets, like `[kworker/0:1]`, and they belong to the kernel, not to any program. (WSL is different: there, PID 2 is part of WSL's own init.)

**PIDs are reused.** The kernel counts up to `pid_max` and then wraps round, skipping numbers still in use. A PID you wrote down an hour ago may now belong to something else. That's one reason to look it up with `pgrep` right before you use it, rather than reusing an old one.

**PID 1 is special.** The kernel won't deliver signals to PID 1 that it hasn't set up a handler for, so `kill -9 1` does nothing. If PID 1 ever exits, the kernel panics, because nothing would be left to adopt orphans. On Ubuntu, Fedora, Debian and Arch, PID 1 is systemd, which also starts and supervises the system's services: [systemd units, targets and dependencies](/g/systemd-units) covers that side.
