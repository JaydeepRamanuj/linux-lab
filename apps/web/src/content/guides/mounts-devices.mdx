  - myth: "`/dev/sda1` always means the same partition."
    reality: "The kernel numbers disks in the order it finds them. Plug in a USB disk before booting and `sdb` may become `sdc`. That's why fstab uses `UUID=` or `/dev/disk/by-uuid/…`, which follow the filesystem, not the order."
  - myth: "Mounting copies the drive's files into the folder."
    reality: "Nothing is copied. The folder becomes a window onto the other filesystem until you unmount it. Files that were already in that folder are hidden, not deleted, and come back after `umount`."
  - myth: "Pulling out a USB stick without ejecting is fine if nothing is copying."
    reality: "Linux keeps written data in memory and writes it to the device later. A copy can look finished while data is still on its way. Ejecting (or `umount`) writes everything out first, and only then is it safe."
  - myth: "`df` and `du` should show the same number."
    reality: "`df` asks each filesystem how full it is, `du` adds up the files it can see. They differ when a deleted file is still open, when a mount hides files underneath it, and because ext4 keeps 5% of the space for root by default."

## The mental model

A disk reaches Linux as a **block device** in `/dev`: `nvme0n1` for an NVMe drive, `sda` for SATA and USB drives. It's divided into **partitions** (`nvme0n1p1`, `sda1`), and each partition holds a **filesystem**, the format that turns raw blocks into folders and files: ext4, vfat, btrfs, NTFS.

A filesystem isn't usable until it's **mounted**: attached to a folder, the **mount point**, in the one tree that starts at `/`. From then on, every path under that folder belongs to that filesystem. When a program opens a path, the kernel finds the deepest mount point the path is under and hands the request to that filesystem:

Most mounts happen without you. At boot, `/etc/fstab` says what to mount; when you plug in a USB stick, the desktop mounts it under `/media/<you>/`. And many mounts aren't disks at all: `/proc`, `/sys`, `/run` and `/dev` are filesystems the kernel makes up, and snaps are compressed image files mounted through **loop devices**, which make a file look like a disk.

## Under the hood

**The fstab fields.** `UUID=… /data ext4 defaults,nofail 0 2` reads: this filesystem, at `/data`, as ext4, with the default options plus `nofail` (don't stop booting if the disk is missing), not backed up by `dump` (0), checked after the root filesystem (2; root itself is 1, 0 skips the check). Find a partition's UUID with `lsblk -f`. Test a new line with `sudo findmnt --verify` and `sudo mount -a`, which mounts everything in fstab that isn't mounted yet, so a mistake shows up now rather than at the next boot.

**Options that change behaviour.** `ro` mounts read-only. `noexec` refuses to run programs from that filesystem, whatever the `x` bits say, and the error is the same Permission denied. `nosuid` ignores [setuid bits](/g/setuid-capabilities) there. `nodev` ignores device files. `/run` and `/dev/shm` are mounted `nosuid,nodev`. `noatime` and `relatime` reduce writes for access times.

**Page cache and unmounting.** Reads and writes go through the page cache in RAM, so a write returns long before it reaches the disk. `umount` (and Eject in the file manager) writes everything out and then detaches. If it says `target is busy`, some process has a file or its working folder on that filesystem; `lsof /media/jd/USB` names it. [File descriptors](/g/file-descriptors) explains what holding a file means.

**Device names.** The kernel names devices in the order it discovers them: `sda`, `sdb`, … for SATA, SCSI and USB; `nvme0n1` for the first NVMe namespace, with partitions `nvme0n1p1`, `p2`. udev adds stable names under `/dev/disk/`: `by-uuid` (the filesystem's ID, set when it's formatted), `by-label`, `by-partuuid` (the partition's ID in the partition table) and `by-id` (the drive's model and serial).

**Filesystems the kernel makes up.** `proc` on `/proc`, `sysfs` on `/sys` and `devtmpfs` on `/dev` exist only in memory. `tmpfs` is a RAM-backed filesystem for `/run`, `/dev/shm` and, on Fedora and Arch, `/tmp`; it can swap out but never touches a disk otherwise. `cat /proc/filesystems` lists every type the running kernel supports; `nodev` marks the ones that don't need a block device.

**Loop devices, squashfs and FUSE.** A loop device presents a file as a block device, so an image file can be mounted like a disk. Every snap is a squashfs image mounted read-only through one, which is why `lsblk` and `df` on Ubuntu list a row of `loop` devices; they're always 100% full and that's normal. FUSE lets an ordinary program provide a filesystem: an AppImage mounts its own image under `/tmp/.mount_…` with FUSE when it starts, which is why the [AppImage scenario](/s/appimage-install) needs `libfuse2`.

**Where the space goes.** `df` reports per mounted filesystem, so a full `/` and an empty `/home` are possible on a machine with two partitions. ext4 reserves 5% of the blocks for root by default, so `Avail` reaches 0 before `Used` reaches `Size`; root's processes and logging keep working, and you can still log in. The [disk full scenario](/s/disk-full) starts with `df -h` for this reason.

**`/etc/mtab`.** It's a symlink to `/proc/self/mounts`, the kernel's own list. `mount` with no arguments and `findmnt` read it. Mounts can also be per process: containers and snaps get their own mount namespace and see a different tree.

**Under WSL**, the root filesystem is a virtual disk (`/dev/sdX` with no partitions), fstab is empty, and Windows drives appear under `/mnt/c` through a `9p` filesystem.
