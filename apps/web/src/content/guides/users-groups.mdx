  - myth: "The kernel checks your username."
    reality: "It checks numbers only. Rename a user and their files stay theirs, because the UID didn't change. Copy files to another machine and they belong to whoever has the same UID there, often a different person."
  - myth: "`sudo usermod -G docker jd` adds jd to the docker group."
    reality: "Without `-a`, `-G` replaces the whole list of extra groups, so jd drops out of `sudo` and the rest. Use `sudo usermod -aG docker jd`, or `sudo adduser jd docker`."
  - myth: "`root` is special because of its name."
    reality: "What matters is user ID 0. Any account with UID 0 is root, whatever it's called. That's one reason to change accounts with the proper tools and never by editing `/etc/passwd` by hand."

    reality: "Anyone who can talk to the Docker daemon can start a container that mounts `/` and changes anything. Membership of `docker` is as good as root; treat it like membership of `sudo`."

## The mental model

Every process carries a **user ID** (UID), a **primary group ID** (GID) and a list of **supplementary groups**. Every file stores one owner UID and one group GID. The [permission check](/g/permissions-model) compares those numbers. Names never enter into it.

Names come from three text files, looked up whenever a program wants to show or accept a name:

| File | One line per | Holds | Readable by |
|---|---|---|---|
| `/etc/passwd` | User | Name, UID, primary GID, home folder, shell | Everyone |
| `/etc/group` | Group | Name, GID, extra members | Everyone |
| `/etc/shadow` | User | Password hash, password age and expiry | root and the `shadow` group |

Your identity is set once, at login, and every process you start inherits it:

That last stage is why `usermod -aG docker jd` seems not to work until you log out and back in: the file changed, but your processes kept the list they were given.

## Under the hood

**Number ranges.** UID 0 is root. On Ubuntu, 1 to 999 are system accounts made by packages (`daemon`, `messagebus`, `systemd-network`), 1000 to 60000 are people (`UID_MIN` and `UID_MAX` in `/etc/login.defs`), and 65534 is `nobody`, an account that owns nothing and is used when a program wants no rights at all. The first person created at install gets 1000. Fedora and Arch use the same ranges.

**Primary and supplementary groups.** The primary group, from `/etc/passwd`, is the group your new files get. The supplementary groups, from `/etc/group`, are extra memberships for the permission check. With `USERGROUPS_ENAB yes`, each user gets a primary group with the same name and number and no other members. That's why Ubuntu's default umask can leave group write on without letting anyone else in.

**Groups with a job.** On Ubuntu:

- `sudo` may use sudo ([how sudo works](/g/how-sudo-works)). Fedora and Arch call it `wheel`.
- `adm` may read logs in `/var/log` and the full journal.
- `plugdev` may mount removable devices; `cdrom` may use optical drives.
- `dialout` may use serial ports such as `/dev/ttyUSB0`, needed for Arduino boards.
- `docker` may control Docker, which is root-equivalent.

**`/etc/shadow`.** Each line holds the password hash, written as `$id$salt$hash`. Ubuntu 24.04 uses yescrypt (`$y$`), set in `/etc/pam.d/common-password`. The `ENCRYPT_METHOD SHA512` in `login.defs` is only used by a few older tools. A `*` or `!` instead of a hash means no password can log in. root's entry is like that on Ubuntu, so root can't log in directly and is reached through sudo. The other fields count days since 1 January 1970: last change, minimum and maximum age, warning period.

**Lookups go through NSS.** `/etc/nsswitch.conf` says where names come from: `passwd: files systemd` means the files first, then systemd's dynamic users. In a company, LDAP or Active Directory lines can be added, and then `getent passwd` finds users that aren't in `/etc/passwd`. That's why `getent` is the reliable way to look someone up, rather than `grep /etc/passwd`.

**Changing accounts.** Use the tools, never an editor on the files: `sudo adduser name` (Debian's friendly front end) or `useradd`; `sudo usermod -aG group name` to add a group; `sudo passwd name` to set a password; `sudo deluser name`. They lock the files, keep `passwd` and `shadow` in step, and refuse a duplicate name. If you must edit by hand, `sudo vipw` and `sudo vigr` lock the files and check them.

**Using a new group without logging out.** `newgrp docker` starts a new shell whose primary group is `docker`; only that shell and what you start from it get the group. Opening a new login, for example `su - $USER` or a new SSH session, picks up the full new list. A desktop session needs a full log out.

**Numbers on files from elsewhere.** A tar archive, a USB disk formatted as ext4, or a container image stores owner numbers, not names. Extract it as root, or plug the disk into another machine, and the files belong to whoever has those numbers there. `ls -l` shows a bare number when no account matches. The [root-owned files scenario](/s/root-owned-files) is the common case where the number is 0.
