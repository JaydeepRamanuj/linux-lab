## The mental model

Every file and folder stores three things the permission check needs: an **owner** (a user ID), a **group** (a group ID) and nine **permission bits**. The bits are three sets of read, write and execute: one set for the owner, one for the group, one for everyone else.

That's the whole rule. "First match wins" explains the strange cases: an owner with fewer rights than others really does get fewer rights.

### Files and folders read the bits differently

| Bit | On a file | On a folder |
|---|---|---|
| `r` | Read the contents | List the names inside |
| `w` | Change the contents | Create, delete and rename entries |
| `x` | Run it as a program | Enter it, and reach anything inside by name |

Two consequences come up all the time:

- **Deleting is a folder permission.** Removing `notes.txt` changes the folder, not the file, so you need `w` and `x` on the folder.
- **Every folder on the path needs `x`.** To open `/home/jd/app/deploy.sh` you need `x` on `/`, `/home`, `/home/jd` and `/home/jd/app`. A folder that is closed to you blocks everything under it, whatever the files' own bits say.

### The numbers

`chmod` also takes the bits as three octal digits, one per class: **read = 4, write = 2, execute = 1**, added up. `755` is `rwxr-xr-x`, `644` is `rw-r--r--`, `600` is `rw-------`. The [chmod numbers scenario](/s/chmod-numbers) has the table and which number to use when.

## Under the hood

**Where the bits live.** Permissions belong to the file's inode, the record that also holds its owner, size and timestamps, not to its name. That's why a hard link to a file has the same permissions under every name. `ls -l` puts the file type in front of the bits: `-` for a regular file, `d` for a folder, `l` for a symlink, `c` and `b` for devices, `s` for a socket and `p` for a pipe.

**Three more bits.** There are twelve bits, not nine. The other three are setuid, setgid and sticky. They show up as `s` or `t` in place of an `x`, and as a fourth, leading octal digit: `/tmp` is `1777`, sticky plus `rwxrwxrwx`. Without the sticky bit, anyone who can write to `/tmp` could delete everyone else's files there.

**Symlinks don't have permissions of their own.** A symlink always shows `lrwxrwxrwx`, and the kernel ignores those bits. It follows the link and checks the target's.

**Scripts need `r` as well as `x`.** To run a compiled program, the kernel needs only `x`: it loads the file itself. A script is different. The kernel reads the `#!` line and starts the interpreter, and the interpreter then has to *read* the script like any other file. So a script with `--x` permissions fails with Permission denied, and `bash deploy.sh` works with only `r`, because there bash is just reading a file. The [Press Enter guide](/g/pressing-enter) covers what happens at that step.

**Execute can be switched off for a whole filesystem.** A filesystem mounted with the `noexec` option refuses to run anything on it, whatever the bits say. Some systems mount `/tmp` or removable drives that way, and the error is the same Permission denied.

**New files and the umask.** A program creating a file asks for a mode, usually `666` for files and `777` for folders. The kernel removes the bits in your umask first. With `022` that gives `644` and `755`. Ubuntu's `/etc/login.defs` sets `UMASK 022`, but also `USERGROUPS_ENAB yes`. At a normal login, that turns the umask into `002` for users whose group has their own name. Your group is only you, so group write does no harm. Shells started some other way, such as a container or WSL, may keep `022`. Run `umask` to see yours.

**A `+` after the bits** in `ls -l` (`-rw-r--r--+`) means the file also has an access control list: extra per-user or per-group rules beyond the three classes. `getfacl` shows them. Most desktop systems never use them.
