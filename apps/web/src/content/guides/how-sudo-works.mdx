## The mental model

The kernel has no "sudo" feature. sudo is a program like `ls`, owned by root and marked **setuid**: when anyone runs it, the process gets root's user ID ([setuid and capabilities](/g/setuid-capabilities) covers the bit). Once it's running as root, sudo decides for itself whether to help you, then starts your command as root and waits for it.

The first stage causes most surprises. Everything your shell does happens as you:

| You type | What happens |
|---|---|
| `sudo echo x > /etc/app.conf` | Your shell opens `/etc/app.conf` first and fails: Permission denied. sudo never ran. Use `echo x \| sudo tee /etc/app.conf`. |
| `sudo cd /root` | `sudo: cd: command not found`. `cd` is part of the shell; there's no program to run. |
| `sudo mytool` | `command not found` if `mytool` is in `~/.local/bin`, which isn't in `secure_path`. Use the full path. |
| `sudo npm install` | Works, but every file it creates belongs to root. See the [root-owned files scenario](/s/root-owned-files). |
| `curl … \| sudo bash` | Only `bash` runs as root, and it runs whatever `curl` downloads. The [curl pipe bash scenario](/s/curl-pipe-bash) shows how to read it first. |

## Under the hood

**Real and effective IDs.** A process has a real user ID (who started it) and an effective user ID (whose rights it has). The setuid bit changes only the effective one. sudo reads the real one to find out who you are, checks the policy, and only then sets both to the target user before running the command. `sudo -u bob cmd` works the same, with bob's IDs.

**The sudoers grammar.** A rule reads `who where = (as_user:as_group) what`. `%sudo` means the group. Ubuntu's file has three rules: `root ALL=(ALL:ALL) ALL`, `%admin ALL=(ALL) ALL` for old installs, and `%sudo ALL=(ALL:ALL) ALL`, then `@includedir /etc/sudoers.d` for extra files. Rules can limit commands (`jd ALL=(root) /usr/bin/systemctl restart nginx`) or drop the password prompt (`NOPASSWD:`). Always edit with `sudo visudo` or `sudo visudo -f /etc/sudoers.d/name`: it checks the syntax before saving, and a broken sudoers file means no sudo at all until you fix it from a recovery boot.

**The password timestamp.** After a successful password, sudo writes a record under `/run/sudo/ts/`, tied to your terminal. For the next 15 minutes, sudo in that terminal doesn't ask; another terminal tab asks again. `sudo -k` forgets it straight away. `/run` is a tmpfs, so a reboot forgets all of them.

**The environment in detail.** With `env_reset`, the command gets a fresh environment: `HOME`, `USER`, `LOGNAME` and `SHELL` for the target user, `PATH` from `secure_path`, `TERM` and `DISPLAY` carried over, and the `SUDO_*` variables. Variables named in `env_keep` survive. `sudo -E` asks to keep the rest, and the policy may refuse. Running `env` as another user through sudo on the test machine showed exactly that list, with `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin`. [How programs inherit their environment](/g/environment-variables) explains why the variables matter.

**`sudo -i`, `sudo -s` and `su`.** `sudo -i` starts root's login shell, in `/root`, with root's startup files. `sudo -s` starts a root shell but keeps your folder. Both are convenient and dangerous: every command you type afterwards runs as root, without a prompt. `su` switches user by asking for the target's password, and root has none on Ubuntu; `sudo su` works but is `sudo -i` the long way.

**The first-run hint.** sudo creates `~/.sudo_as_admin_successful` the first time you use it. Ubuntu's `/etc/bash.bashrc` checks for that file and stops printing its `To run a command as administrator (user "root"), use "sudo <command>".` hint in every new terminal.

**Logging.** Each use is logged through syslog to the journal and to `/var/log/auth.log`, with failures as `a password is required` or `incorrect password attempt`. On a shared machine, that's the record of who changed what.

**Graphical prompts aren't sudo.** The password box that appears when the Software app installs something, or when `systemctl` asks for authentication, comes from polkit, a separate system with its own rules. It also checks membership of `sudo` on Ubuntu, which is why the same password works.

**Elsewhere.** Fedora puts the first user in `wheel` and its sudoers has `%wheel ALL=(ALL) ALL`. Arch ships the `%wheel` line commented out, so you uncomment it with `visudo` after adding yourself to `wheel`.
