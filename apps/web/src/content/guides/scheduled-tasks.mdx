misconceptions:
  - myth: "A cron job runs the same as when I type the command."
    reality: "It runs under `/bin/sh`, from your home folder, with no `.bashrc`, no `.profile`, no terminal and almost no variables: `HOME`, `LOGNAME`, `SHELL`, `PATH` and, on Ubuntu, what `/etc/environment` sets. Aliases, nvm, pyenv and anything else set up in startup files aren't there. Use full paths, or set `PATH` at the top of the crontab."
  - myth: "If the laptop was off at 3 a.m., cron runs the job when it wakes up."
    reality: "Plain cron skips missed runs. anacron, if installed, catches up on daily, weekly and monthly jobs. A systemd timer with `Persistent=true` catches up on any schedule at the next boot."
  - myth: "A cron job's output appears somewhere."
    reality: "cron mails it to you, and most desktops have no mail program, so it's thrown away. The journal says only `No MTA installed, discarding output`. Redirect it yourself: `>> ~/backup.log 2>&1`."
  - myth: "`%` in a crontab command is an ordinary character."
    reality: "cron turns `%` into a new line and feeds everything after the first one to the command as input. `date +%F` breaks in a crontab; write `date +\\%F`."

## The mental model

There are two ways to run something on a schedule, and Ubuntu uses both.

**cron** is a daemon that wakes up every minute, reads its tables, and runs every line whose time matches. A line is five time fields and a command:

```
# min  hour  day  month  weekday   command
  30   2     *    *      *         /home/jd/bin/backup.sh >> /home/jd/backup.log 2>&1
```

That's 02:30 every day. `*` means any value, `*/15` every 15, `1-5` Monday to Friday. Your own table is edited with `crontab -e`; system tables are `/etc/crontab` and the files in `/etc/cron.d/`.

A **systemd timer** is a unit, `backup.timer`, that starts a service unit of the same name, `backup.service`, when its schedule comes round. The service does the work; the timer only says when.

That's the story behind the [apt lock scenario](/s/apt-lock): "right after boot" is when a missed timer catches up. On this test machine, `apt-daily-upgrade.service` started about two minutes after boot and ran for 44 seconds.

Which to choose for your own jobs:

| | cron | systemd timer |
|---|---|---|
| Setup | One line | Two unit files |
| Output | Mailed, or lost | In the journal: `journalctl -u backup` |
| Missed while off | Skipped | Run at next boot with `Persistent=true` |
| Overlap | A slow job can start twice | Never: the service is already running |
| Limits, sandboxing, dependencies | No | Everything a service can do |

cron is fine for a quick personal job. A timer is better for anything you'll need to debug.

## Under the hood

**cron's environment, measured.** A test job running `env` on Ubuntu 24.04 got `HOME=/home/jd`, `LOGNAME=jd`, `SHELL=/bin/sh`, `PWD=/home/jd`, `LANG=C.UTF-8`, and `PATH` from `/etc/environment`, which on Ubuntu includes `/snap/bin`. That `PATH` comes from `pam_env`, which `/etc/pam.d/cron` runs for every job; cron itself is started with `-P`, which tells it not to set one of its own. There's no `DISPLAY` or `DBUS_SESSION_BUS_ADDRESS`, so a job can't open windows or send desktop notifications without help. Why your interactive shell has so much more is in [How programs inherit their environment](/g/environment-variables).

**The `%` rule, measured.** The line `echo first%second; cat > /tmp/pct.txt` ran only `echo first`: the journal logged `CMD (echo first)`, and the rest became the command's standard input. The second command never ran.

**Where cron's tables live.** `crontab -e` edits a copy and installs it to `/var/spool/cron/crontabs/<user>`, checking the syntax first. Don't edit that folder by hand. `/etc/crontab` and `/etc/cron.d/*` are edited directly and have an extra user field. `@reboot`, `@daily` and `@hourly` can replace the five fields. cron logs each run to the journal as `CRON[pid]: (jd) CMD (…)`, so `journalctl -u cron` shows whether a job started, even when its output was lost.

**anacron.** On a machine that's often off, cron's `/etc/cron.daily` line at 06:25 is easy to miss. anacron records when each daily, weekly and monthly folder last ran, and runs it if it's overdue. It's a separate package, and not every install has it; the test machine didn't. That's what the `test -x /usr/sbin/anacron ||` in `/etc/crontab` is for: cron runs the folders itself only when anacron isn't there to do it.

**Timer schedules.** `OnCalendar=` takes calendar events: `daily` is `*-*-* 00:00:00`, `Mon..Fri 09:00` is weekday mornings, `*:0/15` every quarter hour. `systemd-analyze calendar` checks one. Timers can also count from events instead of the clock: `OnBootSec=15min` and `OnUnitActiveSec=1d` mean "15 minutes after boot, then a day after each run", which is how `systemd-tmpfiles-clean.timer` works. `AccuracySec=` (default one minute) lets systemd group nearby wake-ups to save power, and `RandomizedDelaySec=` spreads load.

**A timer for your own job.** Two files in `~/.config/systemd/user/`, then `systemctl --user enable --now backup.timer`:

```ini
# backup.service
[Service]
Type=oneshot
ExecStart=/home/jd/bin/backup.sh

# backup.timer
[Timer]
OnCalendar=*-*-* 02:30
Persistent=true

[Install]
WantedBy=timers.target
```

`systemctl --user start backup.service` runs it once by hand, which is the easiest way to test it. User timers only run while you're logged in, unless lingering is turned on with `loginctl enable-linger`. For a one-off, `systemd-run --user --on-active=10min ./job.sh` creates a temporary timer without writing any files.

**Other distributions.** Fedora uses `cronie`, which is compatible. Arch installs no cron daemon at all and expects timers. Both use systemd timers for their own housekeeping, as Ubuntu does.
