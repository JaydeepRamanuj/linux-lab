misconceptions:
  - myth: "`journalctl` and `/var/log/syslog` are two different logs."
    reality: "On Ubuntu they're mostly the same messages. journald receives them first and forwards a copy to rsyslog, which writes `syslog`, `auth.log` and `kern.log`. The journal has more detail, such as fields and services' plain output. Fedora and Arch don't install rsyslog, so the journal is all there is."
  - myth: "Services write their logs into /var/log."
    reality: "Most systemd services print to stdout and stderr, and journald captures that. Only programs that open their own log files, like nginx (`/var/log/nginx/`) or apt, put text files there. If a service has no file in `/var/log`, run `journalctl -u name`."
  - myth: "The journal will fill the disk if you don't clean it."
    reality: "journald enforces a size cap and deletes its oldest files. Text logs in `/var/log` are kept in check by logrotate, which runs daily. What does fill disks is a program writing its own huge log outside both, or a deleted log file that a program still holds open."
  - myth: "`journalctl` needs sudo."
    reality: "On Ubuntu, members of `adm` can read the whole journal, and every user can read their own entries. `sudo` is needed only if you're in neither `adm` nor `systemd-journal` (on Fedora and Arch, `wheel` works too)."

## The mental model

Most of what you'd call "the logs" on a modern Linux system goes through one program, **systemd-journald**. It collects messages from four places and stores them together in the **journal**:

Alongside the journal, `/var/log` also has logs written by programs **directly**, which never pass through journald: `dpkg.log` and `apt/history.log` from the package tools, `nginx/access.log`, and anything else that opens its own file. These are plain text, so `tail -f` works on them, as in the [watch a log scenario](/s/watch-log).

So "where's the log?" usually has one of three answers:

- **A systemd service**: `journalctl -u name`. Add `-f` to follow, `-n 50` for the last 50 lines, `--since "10 min ago"` to narrow it. The [system service scenario](/s/system-service) starts there.
- **The kernel** (drivers, USB, the out-of-memory killer): `journalctl -k`, or `dmesg`.
- **An app with its own file**: look in `/var/log/<app>/`, or the app's config for a `log` setting.

Every entry has a **priority**, the syslog levels from 0 to 7: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. `-p err` shows `err` and everything more serious.

## Under the hood

**Persistent or not.** journald's `Storage=auto` setting keeps the journal on disk only if `/var/log/journal/` exists, and in memory under `/run/log/journal/` otherwise, lost at every reboot. Ubuntu creates the folder, so the journal survives reboots and `journalctl -b -1` works. If `--list-boots` only ever shows one boot, that folder is missing.

**Size limits.** On disk, the journal may use at most 10% of the filesystem, capped at 4 GB, and it leaves at least 15% free. When it reaches the limit, journald deletes its oldest archived files. To use less, set `SystemMaxUse=` in a drop-in such as `/etc/systemd/journald.conf.d/size.conf`, or trim once with `sudo journalctl --vacuum-size=200M`.

**Fields, not lines.** Each entry is a set of fields. `MESSAGE` is the text and `PRIORITY` the level. The ones journald adds itself start with `_`: `_PID`, `_UID`, `_COMM`, `_SYSTEMD_UNIT`, `_BOOT_ID`, `_TRANSPORT`. A program can't set those, so they can be trusted. `-o verbose` shows them all, `-o json` gives them to scripts, and `journalctl -F _SYSTEMD_UNIT` lists every value a field has taken. `_TRANSPORT` says how the entry arrived: `stdout` for a service's output, `syslog`, `journal` for the native API, `kernel`.

**Why Ubuntu has both.** Ubuntu installs rsyslog, and its systemd package ships a journald drop-in, `/usr/lib/systemd/journald.conf.d/syslog.conf`, that sets `ForwardToSyslog=yes` (upstream's default is `no`). journald passes each message to rsyslog through a socket, and rsyslog sorts them into files by facility, following `/etc/rsyslog.d/50-default.conf`: authentication into `auth.log`, kernel into `kern.log`, and everything except authentication into `syslog`. These are what `grep` and old scripts expect. Fedora, Arch and most container images skip rsyslog, so there's no `/var/log/syslog` there.

**Who can read what.** The journal files belong to the `systemd-journal` group, and an ACL (the `+` in `ls -l`) gives the `adm` group read access too. Fedora and Arch add `wheel` the same way. Members of those groups can read every entry. Other users can read only entries from their own processes. The text files in `/var/log` use plain permissions: `syslog:adm` with mode `640`.

**logrotate.** Text logs would grow for ever, so a daily `logrotate.timer` renames them: `syslog` becomes `syslog.1`, the old `.1` is compressed to `.2.gz`, and the oldest is deleted. Each file's rules live in `/etc/logrotate.d/`; for rsyslog's files it's weekly, keeping four. After rotating, logrotate tells the writer to reopen its file. A program that isn't told keeps writing to the renamed file through its open descriptor, the same thing that makes `tail -f` go quiet: see [file descriptors](/g/file-descriptors).

**Your own messages.** `logger "backup done"` sends a line to the journal through syslog, which is handy in cron jobs and scripts. `systemd-cat` runs a command with its output going into the journal. Your per-user services' output goes to your own part of the journal: `journalctl --user -u name`.
