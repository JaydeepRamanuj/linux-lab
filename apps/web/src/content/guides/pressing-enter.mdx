  - myth: "`which` tells you what will run."
    reality: "`which` only searches `PATH`. Aliases, functions and builtins come first, and `which` doesn't know about them. `type` asks the shell itself."
  - myth: "The program sees the `*` and the `$VAR`."
    reality: "The shell expands them before the program starts. `ls *.txt` hands `ls` a list of file names. If nothing matches, bash passes the pattern through unchanged, so the program gets a literal `*.txt`."
  - myth: "Quotes get passed to the program."
    reality: "Quotes only tell the shell where a word starts and ends and what not to expand. They're removed before the program runs: `echo \"a  b\"` receives one argument, `a  b`, with no quote characters."
  - myth: "`./script.sh` and `bash script.sh` do the same thing."
    reality: "`./script.sh` asks the kernel to run the file, so it needs the `x` bit, and the `#!` line picks the interpreter. `bash script.sh` runs bash, which reads the file as data: it needs only `r`, and the `#!` line is ignored."
  - myth: "`cd` is a program like `ls`."
    reality: "A program runs in its own process, and a process can change only its own working folder. A `cd` program would change folder and exit, leaving your shell where it was. So `cd`, `export` and `source` are builtins: they change the shell itself."

## The mental model

The shell is an ordinary program whose job is to start other programs. Every line you type goes through the same stages. Most error messages tell you which stage failed, once you know the stages.

Two things follow from this, and they explain a lot of confusing behaviour:

- **The program never sees your line.** It gets a finished list of words. Globs, variables, `~` and quotes were all handled by the shell before the program started.
- **A command runs in a separate process.** It can't change your shell. Anything that has to, like `cd`, `export` or `source`, must be a builtin. When a fix says "open a new terminal" or "run `source ~/.bashrc`", that's why.

Each failure maps to a stage:

| Message | Stage | Means |
|---|---|---|
| `syntax error near unexpected token` | Split | A quote or bracket isn't closed, or an operator is out of place |
| `command not found` (127) | Find | Not an alias, function or builtin, and not found on `PATH`. See [command not found](/s/command-not-found) |
| `Permission denied` (126) | Exec | The file was found but isn't executable. See [Permission denied](/s/permission-denied-script) |
| `required file not found`, or `No such file or directory` for a file that exists | Exec | The `#!` interpreter is missing, or bash remembered an old path (both below) |

## Under the hood

**The lookup order, exactly.** Aliases are expanded while the line is split. For the command name that results, bash checks: a function with that name, then a builtin, then its hash table of programs it has found before, then a search of `PATH`. A name with a `/` in it, like `./deploy.sh` or `/usr/bin/python3`, skips all of that and is run as a path. That's why a script in the current folder needs `./`: the current folder isn't on `PATH`.

**Bash remembers where it found things.** After the first `PATH` search, bash keeps the result in a hash table (`hash` lists it). If you then delete or move that program, bash still tries the remembered path. You get `No such file or directory`, even though another copy exists further along `PATH`. `hash -r` clears the table, and so does opening a new terminal.

**`fork` then `exec`.** The kernel has no "start this program" call. A process makes a copy of itself with `fork`, and the copy replaces its own program with `execve`. Everything the child inherits comes from that copy: environment, working folder, open files, user and groups. The [environment variables scenario](/s/env-vars) depends on this: `PORT=4000 npm run dev` sets a variable in that one child only.

**The `#!` line is read by the kernel.** When `execve` gets a file that starts with `#!`, the kernel runs the interpreter named on that line with the script's path as an argument. If that interpreter doesn't exist, the call fails with "no such file". Bash 5.2 (Ubuntu 24.04) reports it as `cannot execute: required file not found`; older versions say `bad interpreter`. A script saved with Windows line endings fails the same way: the interpreter's name ends in an invisible carriage return, `/bin/bash\r`, and there's no such file. A file with no `#!` line and no binary header gets run by bash itself, as a shell script.

**Builtins and pipelines.** Builtins run inside the shell, with no fork. The exception is a builtin in a pipeline: each part of a pipeline runs in its own process, so `cd /tmp | cat` changes the folder of a short-lived child, and your shell stays put. In a pipeline, `$?` is the last command's code unless `set -o pipefail` is on. The [exit codes scenario](/s/exit-codes) covers that.

**Ubuntu's "did you mean" message.** When the lookup fails, bash calls a function named `command_not_found_handle` if one is defined. Ubuntu defines one that suggests packages: `Command 'tree' not found, but can be installed with: sudo apt install tree`.
