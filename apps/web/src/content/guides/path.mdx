misconceptions:
  - myth: "The shell searches the whole disk for a command."
    reality: "It looks only in the folders listed in `PATH`, in order. A program in any other folder is invisible to it until you add that folder or type the full path."
  - myth: "The current folder is always searched."
    reality: "Not unless `PATH` contains it. That's why you type `./deploy.sh`. An empty entry in `PATH` (a leading or trailing `:`, or `::`) does mean the current folder, which is a security risk."
  - myth: "A new folder on `PATH` works everywhere once you add it to `~/.bashrc`."
    reality: "Only in new bash terminals. Open terminals, cron jobs, services and `sudo` each have their own `PATH`."
  - myth: "`which` shows what the shell will run."
    reality: "On Debian and Ubuntu, `which` is a small `sh` script that searches `PATH`. It knows nothing about your aliases, functions, builtins or the hash table. Use `type`."

## The mental model

`PATH` is an ordinary environment variable holding a list of folders, separated by colons. When you type a command name with no `/` in it, and it isn't an alias, a function or a builtin, the shell walks that list from left to right:

Three rules cover almost everything:

- **Order decides.** When two folders have a program with the same name, the earlier folder wins. That's how version managers work: they put their own folder at the front.
- **Only executable files count.** A file with the right name but no `x` bit is skipped, and the search carries on. If that was the only match, you get `Permission denied` (code 126) instead of `command not found` (127).
- **A `/` turns the search off.** `./build.sh`, `bin/tool` and `/usr/bin/python3` are paths. The shell runs exactly that file and never looks at `PATH`.

`command not found` therefore means one of two things: the program isn't installed, or it lives in a folder that isn't on `PATH`. The [command not found scenario](/s/command-not-found) works out which, and [Add a folder to PATH](/s/add-to-path) fixes the second.

## Under the hood

**The hash table.** Searching every folder for every command would be slow, so bash remembers each program's path the first time it finds it. Later runs skip the search. The table belongs to one shell process and starts empty in each new terminal. It goes stale when a program moves: installing a newer copy earlier on `PATH` doesn't take effect until `hash -r`, and deleting the remembered copy gives `No such file or directory`. Changing `PATH` itself clears the table. Zsh does the same, and its command is `rehash`.

**Where `PATH` comes from on Ubuntu.** It's built in layers, at login and as each shell starts:

| Step | Adds |
|---|---|
| `/etc/environment`, read at login by `pam_env` | The system folders, ending in `/snap/bin` |
| `/etc/profile.d/apps-bin-path.sh`, for login shells | `/snap/bin` again, if it's missing |
| `~/.profile`, for login shells | `~/bin` and `~/.local/bin`, but only if they **exist at that moment** |
| `~/.bashrc`, for each interactive bash | Whatever installers and you appended there |

The third row explains a common puzzle. `pip install --user` or `pipx` creates `~/.local/bin` for the first time, and its programs aren't found until you log out and back in, because `~/.profile` checked for the folder at login and skipped it. The [shell startup files guide](/g/shell-startup-files) covers which files run when.

**`sudo` uses its own `PATH`.** Ubuntu's `/etc/sudoers` has `secure_path`, a fixed list of system folders that replaces yours. A tool in `~/.local/bin` or a version manager's folder works without `sudo` and gives `command not found` with it. Run it by its full path, `sudo "$(command -v tool)"`, or install it somewhere system-wide. The fixed list is a defence: otherwise anything that could write to a folder early in your `PATH` could plant a fake `apt` and wait for you to run it as root.

**Programs search `PATH` too.** The search isn't only a shell feature. The C library's `execvp`, Python's `subprocess`, Node's `child_process` and `env` all walk `PATH` the same way. That's how a `#!/usr/bin/env python3` line works: `env` is always at a fixed path, and it finds `python3` on whatever `PATH` it's given.

**The empty entry.** POSIX says a zero-length entry means the current folder. `PATH=:/usr/bin`, `PATH=/usr/bin:` and `PATH=/a::/b` all make the shell run files from wherever you happen to be. It usually creeps in from a line like `export PATH=$EXTRA:$PATH` where `EXTRA` is empty. Look for a leading, trailing or doubled colon in `echo "$PATH"`.

**Folders that don't exist are skipped** silently. A typo in a `PATH` entry gives no error, only programs that can't be found.
