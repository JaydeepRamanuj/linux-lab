  - myth: "DNS changes take 48 hours to propagate."
    reality: "Nothing is pushed anywhere. Every answer carries a TTL, and caches keep it that long. When the TTL runs out, the next lookup gets the new address. With a TTL of 300 that's five minutes; the 48 hours comes from TTLs of a day or two on older records."

## The mental model

Programs don't speak DNS themselves. They call one glibc function, `getaddrinfo("github.com")`, and get back a list of addresses. Everything else happens behind that call, in an order you can read in two files.

When a name fails, the error says which kind of failure it was. These are the messages glibc gives, and programs pass them on:

| Message | What it means |
|---|---|
| `Name or service not known` | DNS answered: the name doesn't exist. Check the spelling. |
| `No address associated with hostname` | The name exists but has no address of the kind asked for. |
| `Temporary failure in name resolution` | No DNS server answered at all. Check the network, then `resolvectl status`. |
| `curl: (6) Could not resolve host` | curl's wording for any of the three. Try `getent hosts NAME`. |

If `getent` finds the name but the program still can't connect, the problem isn't DNS. [Interfaces and routes](/g/interfaces-ip) and [firewalls](/g/firewall-basics) come next.

## Under the hood

**Why a local stub.** Ubuntu points every program at `127.0.0.53` and lets systemd-resolved deal with the real servers. It caches answers for the whole machine, keeps separate DNS servers per interface (so a VPN's company servers answer only for the company's domains), and follows network changes without rewriting `resolv.conf`. `ss -lun` shows it listening on `127.0.0.53%lo:53`. It also listens on `127.0.0.54`, a plainer "proxy" mode that passes DNS messages through mostly untouched, for programs that need that.

**Where the servers come from.** NetworkManager gets DNS servers from DHCP along with the address and gateway ([interfaces and routes](/g/interfaces-ip)) and passes them to systemd-resolved for that interface. `resolvectl dns` lists them. To use different ones, set them on the connection in NetworkManager, or in netplan's `nameservers:` on a server. Setting `DNS=` in `/etc/systemd/resolved.conf` adds global servers. `/etc/resolv.conf` is rewritten either way.

**Records and TTLs.** A DNS answer is a set of records: `A` (IPv4), `AAAA` (IPv6), `CNAME` (this name is an alias of that one), `MX` (mail servers), `NS` (who answers for this domain), `TXT` (free text, used for domain verification). `resolvectl query -t MX gmail.com` or `dig MX gmail.com` asks for one type. Each record has a TTL in seconds, set by whoever runs the domain. `dig +trace example.com` skips the caches and walks the chain itself: the root servers name the `.com` servers (TTL 172800, two days), those name Cloudflare's servers for `example.com`, and those return the address with TTL 300. `sudo resolvectl flush-caches` empties the local cache; the router's and ISP's caches still keep their copies.

**`/etc/hosts` still wins.** It's checked before DNS, it's read on every lookup, and it needs no restart: adding `127.0.0.1 api.myapp.test` takes effect at once for `curl` and the browser, and not for `dig`. Ubuntu writes your hostname there as `127.0.1.1` so the machine can always look itself up, network or not.

**Search domains.** With `search lan` in effect, a name with no dot such as `nas` is also tried as `nas.lan`. That's how short names work on some home and office networks, and why a typo can sometimes find a real machine. The stub's own file says `search .`; the real search domains are in `resolvectl status` per interface.

**Names inside containers.** Docker gives containers on a user-defined network their own DNS server at `127.0.0.11`, which answers container and service names and forwards everything else to the host's servers. That's why `db:5432` works from inside the app's container and fails from your shell on the host. The [sed and awk scenario](/s/sed-awk) has that exact change.

**What DNS can't promise.** A plain DNS answer isn't signed in a way Ubuntu checks by default (`DNSSEC=no/unsupported` above), so whoever answers could lie. HTTPS is what catches that: the server must also prove it owns the name with a certificate. That's one reason install one-liners should use `https://`, as in the [curl pipe bash scenario](/s/curl-pipe-bash).

**Elsewhere.** Fedora also uses systemd-resolved with the same stub. Arch leaves `/etc/resolv.conf` as a plain file until you choose a resolver. WSL writes its own `resolv.conf` pointing at the Windows host, and says so in a comment at the top; `resolvectl status` then shows `resolv.conf mode: foreign`.
