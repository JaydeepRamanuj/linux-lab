## The mental model

Hundreds of programs need to read compressed data, talk TLS or draw text. Instead of each carrying its own copy of that code, one copy sits in a **shared library**, a file ending in `.so` ("shared object"), and every program that needs it uses that file. A security fix to `libssl.so.3` fixes every program that uses it at once, and the code is in memory only once however many programs share it.

The price is that a program can't run on its own. Its file names what it needs, and something has to find those files every single time it starts:

So the error comes from the loader, before the program has done anything. It's always one of two shapes:

| Error | What it means | Usual fix |
|---|---|---|
| `error while loading shared libraries: libfoo.so.2: cannot open shared object file: No such file or directory` | No file with that name anywhere the loader looks. Exit status 127. | `apt-file search libfoo.so.2`, then install that package. |
| ``version `GLIBC_2.38' not found (required by ./app)`` | The file exists, but it's older than the one the program was built against. | A build of the app for your release, or a newer release. Never replace the system's C library. |

## Under the hood

**Sonames: why the number matters.** A library's file carries its official name, the **soname**: `readelf -d /usr/lib/x86_64-linux-gnu/libz.so.1.3 | grep SONAME` prints `libz.so.1`. A program built against it records that soname in its NEEDED list. The library's authors change the number only when they break compatibility, so `libssl.so.1.1` and `libssl.so.3` are different libraries as far as the loader is concerned, and both can be installed side by side. Within one soname, newer versions must keep working with old programs; that's the promise that lets apt update a library under hundreds of programs.

**How Debian names library packages.** One package per soname: `zlib1g` holds `libz.so.1`, `libssl3t64` holds `libssl.so.3`. The `t64` on many names in Ubuntu 24.04 comes from a switch to 64-bit time values on 32-bit systems; package names changed on every architecture, while the file names stayed the same. That's why old instructions say `libfuse2` and the [AppImage scenario](/s/appimage-install) says `libfuse2t64`. Header files and the plain `libfoo.so` link that compilers use are in a separate `-dev` package (`zlib1g-dev`), which you need only to build software.

**The search order in full.** For each name, the loader tries, in order: the program's own `RPATH`, an older field some programs still set when they were built; then `LD_LIBRARY_PATH`; then the program's `RUNPATH`, the newer field (a program that has one ignores its `RPATH`); then `/etc/ld.so.cache`; then the default folders `/lib` and `/usr/lib` and their `x86_64-linux-gnu` subfolders. `LD_DEBUG=libs ./app` prints each path it tries, which settles any argument about where a library came from:

```
find library=libselinuy.so.1 [0]; searching
 search cache=/etc/ld.so.cache
 search path=/lib/x86_64-linux-gnu/glibc-hwcaps/x86-64-v3:…:/usr/lib		(system search path)
  trying file=/lib/x86_64-linux-gnu/libselinuy.so.1
  …
./app: error while loading shared libraries: libselinuy.so.1: cannot open shared object file: No such file or directory
```

**Libraries you install yourself.** `/usr/local/lib` is in Ubuntu's `/etc/ld.so.conf.d/libc.conf`, so `make install` can put libraries there. But the cache doesn't know about them until `sudo ldconfig` runs, which is why a freshly built library can still give "cannot open shared object file". Libraries for one app belong next to that app, found through its `RUNPATH` or a wrapper script that sets `LD_LIBRARY_PATH` just for it. That's how apps in `/opt` work.

**The C library is special.** `libc.so.6` (glibc) and the loader come from one package, `libc6`, and everything on the system depends on them. glibc keeps old programs working through **symbol versions**: a function can exist as `memcpy@GLIBC_2.2.5` and `memcpy@GLIBC_2.14`, and an old program gets the old one. It doesn't work the other way. A program built on a newer system asks for versions an older glibc doesn't have, which is the `GLIBC_2.38 not found` error. Developers who want one binary for many distributions build it on the oldest system they support. Never install a different glibc over the system one: every program, including `apt`, `sudo` and your shell, depends on it.

**Loaded later, by name.** `dlopen()` loads a library while the program runs, for plugins, GPU drivers and optional features. The AppImage runtime does this for FUSE, which is why its error reads `dlopen(): error loading libfuse.so.2` and why `ldd` doesn't list it. The [mounts and block devices guide](/g/mounts-devices) explains what FUSE is used for.

**Static linking.** A statically linked program copies the library code into itself and needs no loader. Most Go programs and many Rust tools are built this way, which is why a single downloaded binary often just runs. The cost is that a security fix in a library needs a new build of every program that copied it.

**Never run `ldd` on a file you don't trust.** For some executables, `ldd` works by running them with a special environment variable, and a malicious file can ignore that and run its own code. `readelf -d` and `objdump -p` only read the file. The ldd(1) man page has the details.
