## The mental model

On Ubuntu, Debian, Fedora and Arch, PID 1 is **systemd**. It starts everything else at boot and then keeps running as a supervisor: it restarts services that crash, stops them at shutdown and records what they print.

Everything systemd manages is a **unit**, and every unit is a small text file. The suffix says what kind:

| Type | Example | What it is |
|---|---|---|
| `.service` | `cron.service` | A program to run and supervise |
| `.timer` | `apt-daily.timer` | Starts a service on a schedule: see [cron vs systemd timers](/g/scheduled-tasks) |
| `.socket` | `syslog.socket` | A socket systemd opens itself, starting the service on the first connection |
| `.target` | `multi-user.target` | A group of units, a named stage of boot |
| `.mount`, `.device`, `.path`, `.slice`, `.scope` | `home.mount` | Filesystems, devices, watched paths and groups of processes |

Units point at each other in two separate ways, and mixing them up is the most common mistake in unit files:

- **Dependency**: *also start that one*. `Wants=` is a soft request: if the other fails, carry on. `Requires=` is strict: if it fails, this unit fails too.
- **Ordering**: *if both are starting, this one goes first*. `After=` and `Before=` only set the order. On their own, they don't start anything.

**Targets** tie boot together. At boot, systemd starts `default.target`, which on a desktop is `graphical.target`. That wants `multi-user.target`, which wants every service enabled for it. Enabling a service means adding it to a target's list:

`systemctl status` shows all of this for one unit: where its file is, whether it's enabled, whether it's running, its cgroup and its latest log lines. The [system service scenario](/s/system-service) uses it to find why a service failed.

## Under the hood

**Where unit files live.** systemd looks in several folders, and a file earlier in the list wins over a file with the same name later:

1. `/etc/systemd/system/`: yours, the administrator's. `systemctl enable` links and `systemctl edit` drop-ins go here.
2. `/run/systemd/system/`: generated at runtime, gone after a reboot.
3. `/usr/lib/systemd/system/`: installed by packages. Don't edit these. On Ubuntu, `/lib` is a link to `/usr/lib`, so `/lib/systemd/system` is the same folder.

`systemctl cat <unit>` prints the file actually in use, followed by any drop-ins, each with its path. `systemd-analyze unit-paths` lists every folder searched.

**Drop-ins.** A file like `/etc/systemd/system/nginx.service.d/override.conf` is merged into the unit, so it only needs the lines you change. `sudo systemctl edit nginx` creates it for you. One catch: list settings such as `ExecStart=` add to the existing value, so to replace the command you first clear it with an empty `ExecStart=` line. After editing unit files by hand, run `sudo systemctl daemon-reload`, or systemd keeps using the old version; `systemctl edit` does that itself.

**Unit file states.** `enabled` has a link from some target. `disabled` has an `[Install]` section but no link. `static` has no `[Install]` section, so it can't be enabled, and is started by something else, like `apt-daily-upgrade.service` by its timer. `masked` is linked to `/dev/null`, so nothing can start it, not even as a dependency; Ubuntu masks `sudo.service` and `hwclock.service` this way. `alias` is another name for a unit.

**Service types.** `Type=` says how systemd knows a service has finished starting. `simple` (cron) counts it as started as soon as the process is running. `exec` waits until the program has actually been executed. `notify` waits for the program to report "ready" over a socket. `forking` is for old-style daemons that fork into the background, and waits for the parent to exit. `oneshot` is for jobs that run and finish, such as `apt-daily-upgrade.service`: the unit is "activating" while it runs and "inactive (dead)" afterwards, with its exit status shown in `status`.

**cgroups.** Each service gets a control group under `/sys/fs/cgroup/system.slice/`. Every process it starts, and every process those start, stays in that cgroup; a process can't leave it by forking or double-forking. That's how `systemctl stop` finds them all, how `status` shows a tree of them, and how limits like `MemoryMax=` apply to the whole service. By default, stopping sends TERM to every process in the cgroup, then KILL after `TimeoutStopSec` (90 seconds): see [signals](/g/signals). `KillMode=process` changes that to the main process only. cron sets it so that jobs it started keep running when cron restarts.

**Socket activation.** A `.socket` unit makes systemd open the socket itself, early in boot. The service starts when the first connection or message arrives, and inherits the open socket as a file descriptor. `rsyslog.service` shows `TriggeredBy: syslog.socket`. That's why services can start in any order without losing messages: the socket exists before the program that reads it. Ubuntu 24.04's SSH server works the same way: `ssh.socket` holds port 22 and starts `sshd` on the first connection ([how SSH works](/g/how-ssh-works)).

**Installing a package often enables it.** On Debian and Ubuntu, a package's install scripts call `deb-systemd-helper` to enable the units it ships and `deb-systemd-invoke` to start them, which is why `apt install nginx` leaves nginx running. `systemctl status` shows `preset: enabled` for the distribution's default. Fedora decides through preset files instead, and leaves most new services disabled until you enable them.

**User units.** A second systemd instance runs for each logged-in user, `user@1000.service` for UID 1000. It reads units from `~/.config/systemd/user/` and the system's `/usr/lib/systemd/user/`, and you manage it with `systemctl --user`, without `sudo`. PipeWire audio and many desktop helpers run there. User units stop when you log out, unless lingering is turned on for that user.
