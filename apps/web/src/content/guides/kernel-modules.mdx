misconceptions:
  - myth: "On Linux you have to install drivers, like on Windows."
    reality: "Almost all drivers come with the kernel package and load on their own when the hardware appears. The exceptions are mostly NVIDIA's own graphics driver and some Wi-Fi chips, which Ubuntu offers under **Additional Drivers**."
  - myth: "`blacklist` in modprobe.d stops a module from ever loading."
    reality: "It only stops automatic loading by hardware alias. `modprobe name` still loads it, and so does another module that depends on it. To block it completely, add `install name /bin/false`."
  - myth: "`lsmod` shows every driver in use."
    reality: "It shows only modules loaded from files. Drivers compiled into the kernel, like ext4 here, never appear. `/sys/module/` and `/lib/modules/$(uname -r)/modules.builtin` include them."
  - myth: "A module works with any kernel."
    reality: "A module is built for one exact kernel version (its `vermagic`), and each kernel has its own folder under `/lib/modules/`. After a kernel update, out-of-tree modules such as NVIDIA's must be rebuilt, which DKMS does automatically."

## The mental model

A **kernel module** is a piece of the kernel kept in its own file (`.ko`, sometimes compressed as `.ko.zst` or `.ko.xz`) under `/lib/modules/<kernel version>/`. Once loaded, it's part of the running kernel, with the same full access as the rest of it. Most modules are **drivers**: the code that knows how to talk to one kind of hardware. Others add filesystems, network protocols or firewall features.

A distribution's kernel can't build in a driver for every device that exists, so it builds in what it needs to boot and ships thousands of modules beside it. You rarely load one by hand. When hardware appears, the kernel and udev find the right module:

The same happens for most hardware at every boot, which is why `lsmod` on a laptop is long without anyone having loaded anything.

## Under the hood

**Driver versus firmware.** A driver is kernel code, running on your CPU. Firmware is a program for the device's own processor (a Wi-Fi chip, a GPU), which the driver uploads when it starts. Ubuntu ships the free drivers inside the kernel package and the firmware files in the `linux-firmware` package, under `/lib/firmware`. "firmware: failed to load …" in the kernel log means the driver is there but the file it needs isn't.

**Which driver is a device using?** `lspci -k` shows each PCI device with a `Kernel driver in use:` line, and `lsusb -t` shows the driver for each USB device. `journalctl -k -b | grep -i -e firmware -e error` lists the kernel's complaints from this boot. `ip link` and `lsblk` show whether the network card or disk the driver should create actually exists.

**Loading and removing by hand.** `sudo modprobe name` loads a module and its dependencies; `sudo modprobe -r name` removes it, and the dependencies if nothing else uses them. It refuses while the module is in use (a nonzero count in `lsmod`). `insmod` and `rmmod` are the low-level versions without dependency handling; prefer `modprobe`. A module loaded by hand is gone after a reboot.

**Making it permanent.** The files in `/etc/modprobe.d/*.conf` take these lines:

| Line | Effect |
|---|---|
| `blacklist name` | Don't load it automatically for hardware |
| `install name /bin/false` | Never load it, even when asked |
| `options name key=value` | Parameters to pass when it loads |
| `softdep name pre: other` | Load `other` first |

Modules to load at every boot, needed or not, go one per line in a file in `/etc/modules-load.d/`, read by `systemd-modules-load.service`. On Ubuntu, `/etc/modules` still works but its own comment calls it obsolete. Settings that matter before the root disk is mounted, such as for a storage or graphics driver, are copied into the initramfs, so run `sudo update-initramfs -u` after changing them ([the boot sequence](/g/boot-sequence)).

**Parameters.** Many modules take options. `modinfo -p name` lists them, and `/sys/module/<name>/parameters/` shows the current values, some of which root can change at runtime ([/proc and /sys](/g/proc-sys)). A parameter can also go on the kernel command line as `name.key=value`, which works for built-in drivers too.

**Out-of-tree modules and DKMS.** Drivers that aren't part of the kernel source, such as NVIDIA's proprietary driver, VirtualBox's modules or some Wi-Fi drivers, come as source code. DKMS builds them for each installed kernel and rebuilds them automatically when apt installs a new kernel. If a driver stops working after a kernel update, `dkms status` shows whether its build for the new kernel succeeded.

**Secure Boot and signatures.** With Secure Boot on, Ubuntu's kernel loads only modules with a valid signature. Canonical signs the modules it ships. For DKMS modules, Ubuntu creates a Machine Owner Key (MOK) on your machine and signs with it, and the key has to be enrolled once: after installing, you set a password, and at the next reboot a text-mode MokManager screen asks you to choose **Enroll MOK** and type it. Skip that screen and the module won't load, which is a common reason a freshly installed NVIDIA driver "does nothing". `mokutil --sb-state` says whether Secure Boot is on.

**Tainting.** Loading a module from outside the kernel's source tree, a proprietary one or an unsigned one sets flags in `/proc/sys/kernel/tainted` and in crash reports. The kernel still works; the flags tell developers that code they can't inspect was running, and many will ask you to reproduce a bug without it.

**Loading modules is a privilege.** It needs root (`CAP_SYS_MODULE`), because a module can do anything the kernel can. That's why services that never need it run with `ProtectKernelModules=yes`, which blocks the [system calls](/g/system-calls) that load modules, and why a kernel in lockdown refuses unsigned ones even from root.

**Under WSL** the kernel is Microsoft's, with most drivers built in and about 900 modules in a separate image mounted at `/lib/modules/`. There's no real hardware to probe, so only a handful load.
