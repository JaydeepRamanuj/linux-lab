## The mental model

When a program ends, it leaves behind one number from 0 to 255. **0 means success. Anything else means some kind of failure**, and the program decides which kind. The number travels from the program, through the kernel, to the parent that started it:

## Under the hood

**Only eight bits.** The kernel's status word has room for one byte of exit code, plus the signal number if a signal ended the process. So `exit 256` reports 0, a success, and `exit 300` reports 44. Programs that want to return a count, such as "number of errors found", cap it below 256 for that reason.

**Signals and 128.** A process killed by a signal never chose an exit code, so the shell makes one up: 128 plus the signal number. That's why codes above 128 usually mean "killed": 137 is SIGKILL (9), often the kernel's out-of-memory killer, and 141 is SIGPIPE (13), a writer whose reader went away, explained in [stdin, stdout, stderr and pipes](/g/standard-streams). A program can also `exit 130` by choice, so the shell's number alone can't tell the two apart. `kill -l 137` prints `KILL`.

**Collecting the status is the parent's job.** Until the parent calls `wait`, the dead process stays in the process table as a zombie. It uses no memory or CPU, only an entry. A few zombies are harmless. Thousands mean the parent program has a bug. If the parent itself dies, its children are adopted by PID 1 (or by a "subreaper" such as your `systemd --user` session), which collects them.

**Builtins and compound commands have statuses too.** `cd` into a missing folder returns 1. A pipeline returns its last command's status, or with `set -o pipefail` the last non-zero one. `! cmd` inverts. An `if` with no branch taken returns 0. A function returns the status of its last command, or the number given to `return`. A syntax error makes bash exit with 2.

**`set -e` in detail.** Bash exits when a command fails, *unless* the failure is being tested. The exceptions are: the condition of `if`, `while` and `until`; any command in an `&&` or `||` list except the last; anything after `!`; and any command in a pipeline except the last. The rule applies to the whole call, so a function called from a tested position runs without `-e` all the way through: in `f || echo failed`, a failing command inside `f` doesn't stop it. Assignments are the other trap: `x=$(false)` on its own line does stop the script, because a plain assignment takes the status of its command substitution, but `local x=$(false)` doesn't, because `local` succeeded. The last three examples above show both.

**Programs choose their own codes.** Most use only 0 and 1. Some document more: `grep` and `diff` use 1 for a negative answer and 2 for trouble, `curl` has over 90 codes, and `timeout` returns 124 when the time ran out. A C header, `sysexits.h`, proposes codes 64 to 78 (such as 64 for bad usage), but few programs follow it. When a code matters, check the program's man page under EXIT STATUS.

**`$?` versus `PIPESTATUS`.** `$?` is a single number, replaced after every command. `PIPESTATUS` is an array with one status per command of the most recent pipeline, a single command counting as a pipeline of one. Both are lost as soon as another command runs, so read them on the next line: `cmd1 | cmd2; s=("${PIPESTATUS[@]}")`.
