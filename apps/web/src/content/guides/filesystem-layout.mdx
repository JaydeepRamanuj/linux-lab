## The mental model

Linux has one folder tree, starting at `/`. There are no drive letters: other disks, USB sticks and even the kernel's own data appear as folders somewhere in that tree. The top-level folders aren't random. Each one answers a question: is this **the system's or yours**, and does it **stay the same or change** while the machine runs?

| Folder | What's in it | Typical question it answers |
|---|---|---|
| `/usr/bin`, `/usr/lib` | Programs and libraries from packages | "Where did apt put `rg`?" |
| `/usr/local` | Software installed by hand for every user | "Where do I put a tool I compiled?" |
| `/opt` | Self-contained apps in one folder each (Chrome lives in `/opt/google/chrome`) | "Where did that vendor's app install?" |
| `/etc` | System-wide configuration, as text files | "Where is the SSH server's config?" |
| `/var/log` | Log files | "Where are the logs?" |
| `/var/lib` | State that programs keep: package database, Docker images | "Why is `/var` so big?" |
| `/var/cache` | Downloaded or computed data that can be rebuilt | "What can I clear?" (`sudo apt clean` empties apt's part) |
| `/home/you` | Your files and your apps' settings | "Where's my stuff?" |
| `/root` | Root's own home folder | "Why can't I open it?" (only root can) |
| `/tmp`, `/var/tmp` | Temporary files, for anyone | "Will this survive a reboot?" (`/tmp`: no) |
| `/media`, `/mnt` | Mounted drives: `/media/you/<label>` for USB sticks, `/mnt` for manual mounts | "Where did my USB stick go?" |

Two rules of thumb cover most decisions. **Outside your home folder, files belong to the system**: change them with `sudo` and only when you know why, and leave `/usr` to the package manager. **Inside your home folder, everything is yours**, including the hidden folders where apps keep their settings and caches, which is often where the space goes in the [disk full scenario](/s/disk-full).

## Under the hood

**The merged `/usr`.** Unix once split programs between `/bin` (needed to boot) and `/usr/bin` (everything else), because `/usr` was often on a second disk that mounted later. Today the early boot happens from an initramfs, so the split no longer helps. Ubuntu, Debian, Fedora and Arch have merged them: `/bin`, `/sbin`, `/lib` and `/lib64` are symlinks into `/usr`. One visible side effect: dpkg knows files by their `/usr` path, so `dpkg -S /bin/ls` finds nothing.

**Vendor defaults in `/usr`, your changes in `/etc`.** Many programs now read their defaults from `/usr/lib` and let a file of the same name in `/etc` override it. systemd units ship in `/usr/lib/systemd/system`, and your overrides go in `/etc/systemd/system`. Kernel settings ship in `/usr/lib/sysctl.d`, and yours go in `/etc/sysctl.d`. The package manager can update `/usr` freely without touching your changes. [systemd units](/g/systemd-units) shows the search order.

**`/var` keeps what changes.** `/var/log` for logs (see [where logs live](/g/journald-logs)), `/var/lib/dpkg` and `/var/lib/apt` for the package database, `/var/cache/apt/archives` for downloaded `.deb` files, `/var/spool` for queued work like mail and cron jobs. `/var/lib` is the one not to clean by hand: it's the programs' memory of what they've done.

**Temporary folders.** `/tmp` is world-writable with the sticky bit (`1777`), so anyone can create files but only the owner can delete them ([setuid, setgid and the sticky bit](/g/setuid-capabilities)). On Ubuntu 24.04 it's an ordinary folder on the root disk. `systemd-tmpfiles` empties it at boot and removes files untouched for 30 days. Fedora and Arch mount a `tmpfs` there instead, so `/tmp` lives in RAM. `/var/tmp` is meant to survive reboots. `/run` is always a `tmpfs`: PID files, sockets and locks that only make sense until the next boot. `/run/user/1000` is your own part of it (`$XDG_RUNTIME_DIR`), readable only by you.

**Your home folder's hidden parts.** The XDG Base Directory spec gives apps four places, each overridable with an environment variable:

- `~/.config` for settings (`$XDG_CONFIG_HOME`)
- `~/.local/share` for data such as fonts, `.desktop` files and the Trash (`$XDG_DATA_HOME`)
- `~/.local/state` for history and logs (`$XDG_STATE_HOME`)
- `~/.cache` for things that can be rebuilt (`$XDG_CACHE_HOME`): safe to delete

`~/.local/bin` is the user's own `/usr/local/bin`. Ubuntu's `~/.profile` adds it to `PATH` when it exists; see [how PATH lookup works](/g/path) and the [add to PATH scenario](/s/add-to-path). Older programs ignore all of this and keep a dotfile or dot-folder directly in `~`, like `~/.bashrc` or `~/.ssh`.

**Where installed software goes.** A `.deb` puts files across the tree: the program in `/usr/bin`, its libraries in `/usr/lib`, default settings in `/etc`, a service unit in `/usr/lib/systemd/system`. `dpkg -L <package>` lists them; `dpkg -S <file>` goes the other way. Snaps live in `/snap` and keep their data in `~/snap`. Programs you unpack yourself, like in the [unpack an archive scenario](/s/extract-archive), go in `/opt` (for everyone, with `sudo`) or `~/opt` (only you).

**Removable media.** When you plug in a USB stick on an Ubuntu desktop, udisks mounts it at `/media/<you>/<label>`. Fedora and Arch use `/run/media/<you>/<label>`. `/mnt` is left for mounts you make by hand. [Mounts and block devices](/g/mounts-devices) explains what mounting is.
