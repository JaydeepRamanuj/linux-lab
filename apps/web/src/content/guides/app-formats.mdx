## The mental model

A [shared library](/g/shared-libraries) is used by many programs, so somebody has to make sure the versions fit. The four formats answer "who?" differently:

- **apt / .deb.** From Ubuntu's archive or a vendor's apt repository. Files go into `/usr` and `/etc` ([the layout](/g/filesystem-layout)). Installing needs root. Updates come with `sudo apt upgrade`, and security fixes install daily. No sandbox. Remove with `sudo apt remove`.
- **Snap.** From the Snap Store, run by Canonical. Each version is mounted at `/snap/<name>/<revision>`, with its data in `~/snap/<name>`. Installing needs root. Updates are automatic, four checks a day. Sandboxed unless the snap is `classic`. Remove with `sudo snap remove`.
- **Flatpak.** Usually from Flathub. Files go to `/var/lib/flatpak`, or `~/.local/share/flatpak` with `--user`, which needs no root; data goes in `~/.var/app/<id>`. Updates come with `flatpak update` or the software centre. Sandboxed. Remove with `flatpak uninstall`.
- **AppImage.** From the project's website. One file, wherever you put it, with no install and no root. Updates are by hand unless the app updates itself. No sandbox. Remove it by deleting the file.

A rule of thumb that holds up: **use apt when Ubuntu has the app**, because it's smallest, shares security fixes with the rest of the system, and is what everything else is tested with. Reach for a Snap or Flatpak when you need a newer version than your release has, or want the app sandboxed. Use an AppImage when the project offers nothing else; the [AppImage scenario](/s/appimage-install) shows how to make one behave like an installed app. A vendor's own `.deb` is fine if it adds an apt repository so it gets updates; a one-off `.deb` doesn't update itself ([install a .deb](/s/install-deb)).

## Under the hood

**Snaps are mounted, not unpacked.** A snap is a single squashfs image. snapd mounts each installed revision read-only at `/snap/<name>/<revision>` through a loop device, which is why `df` and `lsblk` on Ubuntu list a row of `loop` devices at 100% ([mounts and block devices](/g/mounts-devices)). Apps sit on a **base** snap such as `core22`, a minimal Ubuntu userland, so a snap built against 22.04 behaves the same on 24.04 or Fedora. `snap refresh --time` shows the update schedule; on Ubuntu it's `00:00~24:00/4`, four checks spread over the day. `snap refresh --hold` postpones updates and `snap revert <name>` goes back to the previous revision with its data.

**Snap confinement.** A **strict** snap runs under its own AppArmor profile and seccomp filter. It sees its own files, `~/snap/<name>`, and whatever its **interfaces** allow: `home` for your home folder, `network`, `camera`, `removable-media` and so on. `snap connections <name>` lists them, and you can connect or disconnect them. A **classic** snap has no confinement and runs like an apt package; installing one needs `--classic`, which is your cue to trust it like any other software. `--devmode` installs one with the sandbox only reporting, for developers.

**Flatpak runtimes and the sandbox.** A Flatpak app is built against a **runtime**, such as `org.freedesktop.Platform` or `org.gnome.Platform`, which installs once and is shared by every app that uses it, so ten GNOME apps don't carry ten copies of GTK. Installations live in `/var/lib/flatpak` for the whole system or `~/.local/share/flatpak` with `--user`, with no root needed. The sandbox (bubblewrap) starts with almost nothing: no network and no host files except the app's own folder under `~/.var/app/`. Apps ask for more in their manifest, and **portals** let a sandboxed app open a file you pick in a file chooser, print or open a link without broad permissions. Flathub is the main remote, added with `flatpak remote-add`; check an app's listing for whether it's verified and what permissions it asks for.

**AppImages run from a FUSE mount.** An AppImage file is a small program, the runtime, followed by a squashfs image of the app and its libraries. When you run it, the runtime mounts that image with FUSE at `/tmp/.mount_<name>XXXXXX` and starts the app from there; the mount disappears when the app exits. Older runtimes load `libfuse.so.2` with `dlopen`, so on Ubuntu 22.04 and later they fail until you install `libfuse2t64`. The newer, statically linked runtime doesn't need it. Without FUSE at all, `./app.AppImage --appimage-extract-and-run` unpacks to a temporary folder instead, and `--appimage-extract` unpacks into `squashfs-root/` for a look inside. An AppImage still uses your system's glibc, so it's built on an old distribution to run on new ones; one built on a newer system than yours fails with the `GLIBC_… not found` error.

**Why Ubuntu ships Firefox as a snap.** Mozilla builds and publishes the snap itself, so one build reaches every Ubuntu release at once instead of Ubuntu repackaging each version for each release. The apt package `firefox` is a transitional package that installs the snap. Mozilla also runs its own apt repository for people who want a `.deb`; adding it means pinning its packages above Ubuntu's, as in the pin files described in [what a package is](/g/what-is-a-package).

**Other distributions.** Fedora and Linux Mint ship Flatpak and favour it for desktop apps; Mint disables snap support by default. Snaps work on Fedora and Arch once snapd is installed, but strict confinement relies on AppArmor features that not every kernel has; where they're missing, `snap debug confinement` prints `partial` instead of `strict`, and the sandbox is weaker. AppImages run anywhere with a new enough glibc and, for the older runtime, FUSE 2.
