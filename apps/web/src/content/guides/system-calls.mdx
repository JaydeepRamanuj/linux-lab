## The mental model

A **system call** is a request from a program to the kernel, identified by a number: `read` is 0 on x86-64, `write` 1, `openat` 257, `execve` 59. Linux has a few hundred of them, and together they're the whole interface between user space and the kernel. Programs rarely make them directly. They call functions in the C library, such as `read()` or `fopen()`, and the library makes the system call.

Even a tiny command makes many of these. Traced on the test machine, `true` made 30 system calls, `cat /etc/hostname` about 60, and `ls -l /etc` over 700. Most of them come before the program's own code runs: the loader opening and mapping [shared libraries](/g/shared-libraries), setting up memory and loading locale files.

## Under the hood

**Watching with strace.** `strace cmd` runs a command and prints every system call it makes, with arguments and results, to stderr. The options you'll use most:

| Option | Does |
|---|---|
| `-e trace=openat` | Only these calls |
| `-e trace=%file` | Every call that takes a file name |
| `-f` | Follow child processes |
| `-o file` | Write the trace to a file |
| `-s 200` | Show more of each string |
| `-c` | Count calls and time, as a table |
| `-p PID` | Attach to a running process |

`-p` needs permission to trace the process. Ubuntu sets `kernel.yama.ptrace_scope = 1`, which lets you trace only your own children, so attaching to an already running program takes `sudo strace -p PID`. strace uses `ptrace`, the same mechanism debuggers use, and slows the traced program down noticeably.

**Errors are numbers.** When a call fails, strace shows the name and text. Two real ones: `ls /nonexistent` ends with a `statx` call returning `-1 ENOENT (No such file or directory)`, and `echo hi > /root/x` as a normal user shows the shell's

```
openat(AT_FDCWD, "/root/x", O_WRONLY|O_CREAT|O_TRUNC, 0666) = -1 EACCES (Permission denied)
```

The ones you'll meet most:

| Name | The message you see |
|---|---|
| `ENOENT` | No such file or directory |
| `EACCES` | Permission denied |
| `EPERM` | Operation not permitted |
| `EEXIST` | File exists |
| `EADDRINUSE` | Address already in use |
| `ENOSPC` | No space left on device |
| `EMFILE` | Too many open files |
| `EAGAIN` | Resource temporarily unavailable |

`EACCES` and `EPERM` look alike but differ: the first is a failed permission check on a file ([the rwx model](/g/permissions-model)), the second an operation that needs a privilege you lack, such as changing a file's owner. `ENOENT` from `execve` can mean the program's interpreter is missing rather than the file itself, which is why a script with a bad `#!` line, or Windows line endings, says `cannot execute: required file not found` ([the permission denied scenario](/s/permission-denied-script)).

**Finding what a program reads.** "Which config file is it actually using?" is answered by `strace -f -e trace=openat,statx prog 2>&1 | grep -v ENOENT`: every file it opened or looked at, minus the ones that don't exist. Leave the `grep` out to also see the places it searched in vain, which shows the search order.

**Waiting is a system call too.** A program waiting for input, a network reply, a child process or a timer is inside a system call (`read`, `poll`, `wait4`, `clock_nanosleep`), and the process sleeps until the kernel has an answer. `ps` shows it as `S` (sleeping, can be woken by a signal) or `D` (uninterruptible, usually disk or network I/O, which even SIGKILL has to wait for). The `WCHAN` column in `ps -o pid,stat,wchan:20,comm`, or `/proc/<PID>/wchan`, names the kernel function it's waiting in. [Signals](/g/signals) covers how a signal interrupts a waiting call.

**The vDSO.** Some calls are made so often, and change so little, that the kernel offers them without the switch to kernel mode. It maps a small library, the vDSO, into every process; on x86-64 it provides `clock_gettime`, `gettimeofday`, `time` and `getcpu`. The C library uses it automatically, so a program checking the clock thousands of times a second stays fast.

**Filtering system calls.** A process can ask the kernel to refuse any call outside a list, using seccomp. systemd uses this for its own services: `SystemCallFilter=` in a unit file, and settings like `ProtectKernelModules=yes`, which blocks the calls that load [kernel modules](/g/kernel-modules). On the test machine `systemd-timesyncd` runs with `Seccomp: 2` in its `/proc/<PID>/status`, meaning a filter is active; your shell shows `0`. Container runtimes such as Docker apply a default filter too, and browsers sandbox their tabs the same way.

**Numbers differ by architecture.** `read` is 0 on x86-64 but 63 on 64-bit ARM, and the registers differ too. strace and the C library handle this for you; it only matters if you read raw numbers, as in `/proc/<PID>/syscall`.
