  - myth: "Everything is a file, so everything is stored on the disk."
    reality: "Only regular files, folders and symlinks live on a disk. Devices, sockets, pipes and everything in `/proc` and `/sys` are names that lead to the kernel. They take no disk space, and most of them vanish when the machine turns off."
  - myth: "`/dev/null` is a file that slowly fills up."
    reality: "It's a driver with a name. Writes to it are thrown away and report success, and reads from it end at once. Its size is always 0, however much you send to it."
  - myth: "The `.sh` or `.txt` at the end decides what a file is."
    reality: "The kernel ignores extensions. The type (file, folder, device and so on) is stored in the inode, and whether a file runs depends on its `x` bit and its first bytes. Desktop apps use extensions to choose an icon or a program to open it with; the kernel doesn't."
  - myth: "Literally everything has a file name."
    reality: "Most things do, not all. Network interfaces like `eth0` have no entry in `/dev`, and a TCP connection has no path; a program sees it only as a file descriptor. `/sys/class/net` and `/proc` describe them as files, but you can't open an interface and read packets from it."

## The mental model

A program that wants to use something calls `open()` on a name, gets back a [file descriptor](/g/standard-streams), and then calls `read()` and `write()` on it. "Everything is a file" means Linux puts as many kinds of things as it can behind that same small set of calls, under names in the same folder tree.

So `cat` can show a text file, a kernel counter in `/proc` or the bytes of a disk, without knowing which is which. `> /dev/null` throws output away because `/dev/null` accepts writes like any file and keeps nothing. The [redirection scenario](/s/redirection) relies on exactly that.

Underneath, every name leads to one of seven file types. `ls -l` shows the type as the first letter:

| Type | What reading and writing it does | Made by |
|---|---|---|
| Regular file | Reads and writes bytes stored on a disk | Any program that writes a file |
| Directory | Holds names, each pointing at an inode | `mkdir` |
| Symlink | Holds a path; opening it opens that path instead | `ln -s` |
| Character device | Talks to a driver, a stream of bytes (terminals, `/dev/null`, random numbers) | The kernel and udev, in `/dev` |
| Block device | Talks to a driver in fixed-size blocks (disks, partitions, USB sticks) | The kernel and udev, in `/dev` |
| Socket | A connection point another program listens on | The listening program |
| Named pipe | A pipe with a name: one program writes, another reads | `mkfifo` |

## Under the hood

**One layer above every filesystem.** The kernel's virtual file system (VFS) receives every `open()`, `read()` and `write()`. It looks at what the name leads to and hands the call on: to ext4 for a file on your disk, to the null driver for `/dev/null`, to the `proc` code for anything under `/proc`. Programs only ever talk to the VFS, which is why the same tools work everywhere.

**Device numbers.** A device file holds no data. It holds two numbers: the **major** number picks the driver, and the **minor** number picks which device that driver means. `/dev/null` is `1, 3` and `/dev/zero` is `1, 5`: the same "memory devices" driver, two different behaviours. `/dev/sda` is `8, 0`, the first SCSI-style disk; `8, 1` would be its first partition. On current systems the kernel creates these nodes itself on a `devtmpfs` mounted at `/dev`, and udev adds permissions and friendly symlinks such as `/dev/disk/by-uuid/…`. [Mounts and block devices](/g/mounts-devices) uses those names.

**Character versus block.** A character device is read as a stream, byte by byte in order: a terminal, a serial port, the random generator. A block device is read in blocks at any position, which is what a filesystem needs, and the kernel caches those blocks in memory. Disks and partitions are block devices.

**Some useful devices:**

- `/dev/null` discards writes and returns end-of-file on read.
- `/dev/zero` returns zero bytes for as long as you read.
- `/dev/urandom` returns random bytes from the kernel's generator, the same one programs use to make keys.
- `/dev/tty` is your terminal, whatever its real name is (`/dev/pts/0` in a terminal window). Programs open it to ask for a password even when stdin is a pipe.
- `/dev/stdin`, `/dev/stdout` and `/dev/stderr` are symlinks to `/proc/self/fd/0`, `1` and `2`.

**Sockets and pipes with names.** A Unix socket bound to a path shows up in the tree as type `s`. The path is only a meeting point: nothing is written to the disk, and data goes straight between the two programs through the kernel. A network socket (TCP or UDP) has no path at all; [ports and sockets](/g/ports-sockets) shows how to find it from its port instead. A named pipe made with `mkfifo` works like the `|` in a shell, except that the two programs find it by name: whatever one writes, the other reads.

**Where the model stops.** Directories are files, but `cat /etc` says `Is a directory`; programs list them with special calls. Network interfaces have no device file. And plenty of control happens through `ioctl()`, a catch-all call for operations that don't fit read and write, such as setting a terminal's size. The idea is a strong default, not a law.

**`/proc` and `/sys`.** The kernel also describes itself as files: every process gets a folder in `/proc`, and every device and driver a folder in `/sys`. [/proc and /sys](/g/proc-sys) covers them.
