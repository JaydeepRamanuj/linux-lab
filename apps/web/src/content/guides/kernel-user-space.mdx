## The mental model

The CPU has (at least) two modes. In **kernel mode** code can do anything: touch any memory, talk to any device, stop any program. In **user mode** it can only compute on its own memory. The **kernel** is the program that runs in kernel mode, loaded at boot from `/boot/vmlinuz`. Everything else runs in user mode, in **user space**: your shell, your browser, `systemd`, and programs run as root.

A program in user space can't open a file, allocate memory, start another program or send a packet on its own. It asks the kernel, through a **system call**, and the kernel decides whether to do it:

The kernel's jobs, roughly:

| Job | What it means for you |
|---|---|
| Processes | Starts and stops them, and shares the CPUs between them many times a second |
| Memory | Gives each process its own private memory, uses spare RAM as disk cache |
| Files | Turns disks into folders and files, and enforces permissions |
| Devices | Drivers for disks, USB, graphics, Wi-Fi, keyboards |
| Network | TCP/IP, sockets, firewall rules |
| Security | Users, capabilities, namespaces, AppArmor |

So "Permission denied", "No such file or directory" and "Address already in use" are all the kernel answering a request. The program only prints the answer.

## Under the hood

**Two modes, enforced by the CPU.** On x86 the modes are called ring 0 (kernel) and ring 3 (user). User-mode code that tries a privileged instruction, or touches memory it doesn't own, causes a CPU exception, and the kernel kills the process: that's `Segmentation fault`. The only ways into kernel mode are system calls (a program asking), interrupts (hardware asking, such as a key press or a finished disk read) and exceptions (a page fault or an error). [System calls](/g/system-calls) shows the first in detail.

**Every process has its own address space.** Memory addresses in a program are virtual: the kernel and the CPU's memory-management unit map them to real RAM page by page (4 KiB on x86). Two programs can use the same address and see different data. The kernel's own memory is mapped into every process too, but marked kernel-only, so a system call doesn't have to switch maps. When a program touches a page that isn't in RAM yet, the CPU raises a page fault, the kernel fills the page (from the program file, from swap, or with zeros) and the program carries on without knowing.

**Root is not the kernel.** Root is user ID 0, and the kernel skips most permission checks for it, through [capabilities](/g/setuid-capabilities). But root runs in user space like everyone else. `/dev/mem` and `/proc/kcore` exist for debugging, and on a kernel in lockdown mode (Ubuntu turns it on with Secure Boot) even root can't use them to read or change the kernel. The way to run your own code in kernel mode is a [kernel module](/g/kernel-modules), which needs root and, with Secure Boot, a signature.

**The kernel's own threads.** The kernel has work that belongs to no program: flushing data to disk, handling network queues. It does it in kernel threads, which show up in `ps` in square brackets, children of PID 2 (`kthreadd`). [Processes, PIDs and the tree](/g/processes-basics) covers them and why WSL looks different.

**Reading CPU time.** `top`'s `%Cpu(s)` line splits the time: `us` is programs running their own code, `sy` the kernel working for them, `wa` waiting for the disk, `hi`/`si` interrupts, `st` time stolen by a hypervisor in a virtual machine. `time` gives the same split for one command. Copying, listing and networking are mostly `sy`; number crunching is all `us`.

**When memory runs out.** The kernel hands out memory lazily and lets programs reserve more than exists, betting they won't all use it. When RAM and swap really run out, the **OOM killer** picks a process, usually the biggest, and kills it with SIGKILL. It logs `Out of memory: Killed process …` in the kernel log, which is why the [CPU and RAM hog scenario](/s/cpu-ram-hog) points at `journalctl -k`.

**The kernel's log.** Drivers and the kernel write to a ring buffer in memory, which `dmesg` prints and journald copies into the journal. Ubuntu builds its kernels with `dmesg_restrict` on, so `dmesg` as a normal user fails with `Operation not permitted`; `sudo dmesg` works, and so does `journalctl -k` for members of `adm` ([where logs live](/g/journald-logs)). `/etc/sysctl.d/10-kernel-hardening.conf` explains the setting.

**Kernel versions on Ubuntu.** Ubuntu 24.04 shipped with kernel 6.8. Security fixes arrive as new builds of the same version (`6.8.0-84`, `6.8.0-85`…), installed by apt like any package, and used after the next reboot. Later point releases also offer newer HWE (hardware enablement) kernels for new hardware. Old kernels stay installed for a while so you can pick one from the boot menu if a new one misbehaves.

**Under WSL**, Windows runs a lightweight virtual machine with Microsoft's build of the Linux kernel (`microsoft-standard-WSL2`), shared by all your WSL distributions. Ubuntu's own kernel packages aren't installed and `/boot` is empty; the kernel is updated by `wsl --update` from Windows.
