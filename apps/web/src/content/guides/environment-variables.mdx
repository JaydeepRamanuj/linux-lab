## The mental model

Every process has an **environment**: a list of `NAME=value` strings, set when the program starts. When a process starts another one, it hands over a copy of the list. The new process can change its copy as much as it likes, and the parent's copy stays as it was.

That one rule, copies flow down and never up, explains the usual surprises:

- **A script can't change your terminal.** It runs as a child. That's why setup scripts tell you to `source` them, which runs them inside your shell instead.
- **A new value needs a restart.** A running editor or server keeps the copy it started with.
- **Each terminal is separate.** Two terminals are two shells, each with its own copies. An `export` in one doesn't reach the other. Lines in a startup file run in every new shell, which is how a setting becomes permanent. See [shell startup files](/g/shell-startup-files).

The [environment variables scenario](/s/env-vars) covers the three ways to set a variable (`VAR=x`, `export`, `VAR=x cmd`) and `.env` files.

## Under the hood

**Where the list lives.** `execve` takes the program, the argument list and the environment list. The kernel copies the strings onto the top of the new program's stack, next to the arguments. The C library exposes them as `environ`, and `getenv` searches that array. There's no central store of variables anywhere: each process has its own block of memory.

**`/proc/<pid>/environ` is the starting copy.** It shows the environment as it was when the program started. If the program later changes its variables, the file doesn't follow. Your shell is a good example: run `export LATE=1`, and `LATE` still isn't in `/proc/$$/environ`, because bash keeps its variables in its own tables and only builds a fresh list when it starts a program. The file is readable only by the process's owner and root, because environments often hold tokens.

**Arguments and environment share one limit.** The kernel caps the combined size of the arguments and environment passed to `execve`. On a typical system that's 2 MB (`getconf ARG_MAX` prints `2097152`), a quarter of the stack size limit. When a command fails with `Argument list too long`, a huge environment counts against the same budget as the arguments.

**What bash adds and leaves out.** When bash starts, it sets `PWD`, `SHLVL` (how many shells deep you are) and `_` (the last argument of the previous command). With no `PATH` at all, it sets a default one for its own lookups but doesn't export it, which is why `env -i bash -c env` shows no `PATH`. Arrays can't be exported: `export arr` copies nothing. Functions can, with `export -f`: bash passes them as specially named variables like `BASH_FUNC_name%%`.

**Who doesn't read your shell files.** A variable only reaches a process if something on its way down the tree set it:

| Started by | Gets |
|---|---|
| A terminal (bash) | Login environment plus whatever `~/.bashrc` exports |
| The desktop (dock, app menu) | Login environment. On Ubuntu the graphical login reads `~/.profile`, not `~/.bashrc` |
| `sudo` | A fresh, small environment: `env_reset`, and `secure_path` as `PATH`. `sudo -E` asks to keep yours, if the policy allows |
| cron | A handful of variables (`SHELL`, `HOME`, `LOGNAME`), plus `/etc/environment` on Ubuntu. Nothing from your shell files |
| systemd services | Only what the unit file sets with `Environment=` or `EnvironmentFile=` |

So a tool that works in your terminal but fails in cron, a service or under `sudo` is very often a missing variable, with `PATH` the most common one. The [PATH guide](/g/path) covers that case.

**`/etc/environment` isn't a script.** It's read at login by the `pam_env` module as plain `NAME=value` lines. `$HOME`, `export` and `if` don't work there. Fedora and Arch use the same file through the same module.

**Names.** Variable names are case-sensitive. By convention, exported variables are UPPER_CASE, and lowercase names are used for shell-local variables, so a local `path` can't clobber `PATH` by accident.
