misconceptions:
  - myth: "A hard link is a shortcut to the original file."
    reality: "A hard link is a second name for the same inode, as real as the first. There is no original: delete either name and the other keeps working. The data goes away only when the last name is gone and no process has it open."
  - myth: "`ctime` is the creation time."
    reality: "It's the change time: when the inode last changed, which includes a `chmod`, a `chown` or a rename. The creation time is `Birth` in `stat`, which ext4 and btrfs record and older filesystems don't."
  - myth: "`mv` copies the file and deletes the old one."
    reality: "Within one filesystem, `mv` only renames: it writes a new folder entry for the same inode and removes the old one, so a 50 GB file moves instantly. Only across filesystems, such as to a USB stick, does it copy and then delete."
  - myth: "Removing a symlink can delete what it points to."
    reality: "`rm link` removes only the link. The danger is a trailing slash: `rm -r link/` follows the link and deletes the contents of the target folder. The [symlink scenario](/s/symlink-shortcut) shows it."

## The mental model

A filesystem keeps two kinds of things. An **inode** is the file itself: its data blocks, size, owner, permissions and timestamps, identified by a number. A **folder** is a small table of **names**, each pointing at an inode number. The name isn't stored in the inode at all.

That gives two kinds of link:

| | Hard link (`ln`) | Symlink (`ln -s`) |
|---|---|---|
| What it is | Another name for the same inode | A separate inode holding a path |
| If the target's name is deleted | Still works: the data is still there | Breaks: `No such file or directory` |
| Across filesystems or drives | No (`Invalid cross-device link`) | Yes |
| To a folder | No | Yes |
| Permissions | The file's own, shared by every name | Always `rwxrwxrwx`; the target's count |
| `ls -l` shows | A link count above 1 | `l` and `-> target` |

Symlinks are what you'll make day to day, as in the [symlink scenario](/s/symlink-shortcut). Hard links matter mostly for understanding what commands do to files:

| Command | What happens to the inode |
|---|---|
| `rm name` | Removes one name; the link count drops by one |
| `mv a b` on one filesystem | Same inode under a new name. Instant, whatever the size |
| `mv a /media/usb/` | New inode on the other filesystem, then the old name is deleted |
| `cp a b` | A new inode with a copy of the data |
| `echo x > a` | Same inode, contents replaced |
| `sed -i …` and many editors' save | A new file renamed over the old name: a new inode |

That last row has a consequence: after `sed -i` edits one name of a hard-linked file, the two names point at different inodes, and the other one still has the old text. The [mv and cp overwrite scenario](/s/safe-mv-cp) is the same mechanism from the other side: `mv` replacing a name drops the old inode's last link.

## Under the hood

**When data is really freed.** Each inode counts its names, and the kernel separately tracks how many open files point at it. The blocks are freed only when both reach zero. That's why a deleted log that a process still has open keeps filling the disk. [File descriptors](/g/file-descriptors) covers that case and how to find it with `lsof +L1`.

**Folders are files of names.** A folder's data is the list of names and inode numbers inside it. Every folder also contains `.` (itself) and `..` (its parent), and both are hard links. That's where folder link counts come from: an empty folder has 2 (its name in the parent and its own `.`), and each subfolder adds one through its `..`. Linux doesn't allow hard links to folders (`hard link not allowed for directory`), because a folder with two parents could make loops that tools walking the tree would never leave.

**Inode numbers are per filesystem.** Inode 2 is the root folder of every ext4 filesystem, so the same number can exist on each disk. A file is identified by its device plus its inode number, which is why hard links can't cross filesystems. Renaming across them fails the same way inside the kernel (`EXDEV`), and `mv` falls back to copy and delete. Moving a file from `/tmp` to `/dev/shm` gave it a new inode number.

**Running out of inodes.** ext4 decides the number of inodes when the filesystem is created and can't add more. One inode per file, however small, so a folder of millions of cache or session files can use them all up. Writes then fail with `No space left on device` although `df -h` shows space free; `df -i` shows `IUse%` at 100%. btrfs and XFS allocate inodes as needed and rarely hit this.

**Symlinks in detail.** A symlink's content is a path, stored as text and not checked when you make it: `ln -s /nope broken` succeeds, and only opening it fails. A relative target is resolved from the folder the link sits in, not from where you ran `ln`. Short targets fit inside the inode itself (a 9-byte link used 0 blocks; a 67-byte one used a block). The kernel ignores a symlink's own permissions and checks the target's, and `chmod link` changes the target. `ls -l` shows one level of a link; `readlink -f` and `namei` follow the whole chain.

**Protected links.** Ubuntu sets `fs.protected_hardlinks = 1` and `fs.protected_symlinks = 1`. The first stops you from hard-linking a file you don't own and can't write: `ln /etc/passwd ~/pw` fails with `Operation not permitted`, even on the same filesystem. The second stops a process from following a symlink in a sticky, world-writable folder like `/tmp` when the link's owner is someone else, which blocks a classic way to trick a root program into writing the wrong file.

**Counting space.** `du` counts each inode once, however many names it has: two 1 MB names for one inode add up to 1 MB. `du --count-links` counts them twice. `ls -l` shows each name's size, so adding up `ls` can overstate. Backup and sync tools that preserve hard links (`rsync -H`, `cp -a`) do the same bookkeeping.

**The four timestamps.** `Access` (atime) is the last read, though the default `relatime` mount option updates it only when the file has changed since, or once a day. `Modify` (mtime) is the last change to the data. `Change` (ctime) is the last change to the inode, data included. `Birth` is when the inode was created. `ls -l` shows mtime; `ls -lu` and `ls -lc` show atime and ctime.
