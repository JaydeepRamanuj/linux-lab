misconceptions:
  - myth: "`kill` means kill."
    reality: "`kill` sends a signal, TERM unless you name another. TERM is a request: a well-behaved program saves, cleans up and exits. `kill -STOP`, `kill -CONT` and `kill -HUP` don't end anything, and many daemons treat HUP as \"reload your config\"."
  - myth: "`kill -9` is the proper way to stop a process."
    reality: "It's the last resort. KILL gives the program no chance to finish writing files, remove lock files or tell its children to stop. Send TERM, wait a few seconds, and use `-9` only if it's still there."
  - myth: "Ctrl+C kills the program."
    reality: "Ctrl+C sends INT, which a program can catch. Python turns it into `KeyboardInterrupt`, editors and REPLs use it to cancel the current line, and a program can ignore it completely. If Ctrl+C does nothing, Ctrl+\\ (QUIT) is the next step, and `kill` from another terminal after that."
  - myth: "A process that ignores `kill -9` has found a way to block it."
    reality: "Nothing can block KILL. If the process is still listed, it's either a zombie (already dead, waiting for its parent) or in state `D`, stuck inside a kernel call to a disk or network drive. The signal waits and takes effect the moment that call returns."

## The mental model

A **signal** is a small numbered message sent to a process. The kernel delivers it, and the process can be told about it at almost any moment, in the middle of whatever it's doing. Signals come from three places:

- **Other processes**, through `kill`, `pkill` or systemd stopping a service.
- **The terminal**, when you press Ctrl+C, Ctrl+Z or Ctrl+\\, or close the window.
- **The kernel itself**, when a process does something it can't allow (SEGV for a bad memory access), when a pipe's reader goes away (PIPE), or when a child exits (CHLD).

For each signal, a process has one of three settings: do the **default** action, **ignore** it, or **catch** it with its own handler function. What happens on arrival:

The signals worth knowing by name:

| Signal | Sent by | Default |
|---|---|---|
| TERM (15) | `kill`, `pkill`, systemd stopping a service | end |
| INT (2) | Ctrl+C | end |
| QUIT (3) | Ctrl+\\ | end, with a core dump |
| KILL (9) | `kill -9`, the out-of-memory killer, systemd after a timeout | end, can't be caught |
| HUP (1) | the terminal closing | end |
| TSTP (20) | Ctrl+Z | pause |
| STOP (19) | `kill -STOP`, debuggers | pause, can't be caught |
| CONT (18) | `fg`, `bg`, `kill -CONT` | resume |

That's the whole reason the [frozen app scenario](/s/frozen-app) tries TERM first and KILL second. TERM asks the program, so a frozen program never gets round to answering. KILL never asks.

## Under the hood

**Exit codes record the signal.** A process ended by a signal didn't choose an exit code, so its parent learns "killed by signal N" instead, and the shell reports 128 + N: 130 after Ctrl+C, 137 after `kill -9`, 143 after a plain `kill`, 129 after a hang-up. `kill -l 137` turns it back into a name. [How exit status works](/g/exit-status) has the rest.

**Ctrl+C goes to a whole group.** The terminal doesn't know about PIDs. When you press Ctrl+C, the terminal driver sends INT to every process in the terminal's **foreground process group**. In `sleep 100 | sleep 101`, both processes get it and both die, so `PIPESTATUS` reads `130 130`. Job control, process groups, and why background jobs don't get your Ctrl+C are in [Jobs, sessions and closing the terminal](/g/jobs-sessions).

**Stopped processes and pending signals.** A process paused with Ctrl+Z or STOP runs no code, so it can't run a handler either. If it has no handler, a TERM still ends it on the spot, because the default action needs nothing from the program. If it does have a handler, the TERM waits, pending, until the process is continued. On a stopped Python program with a TERM handler, `/bin/kill PID` did nothing visible, and bash's `kill %1` worked at once: bash's built-in `kill` sends CONT along with the signal when the target is a stopped job.

**Signals arrive between instructions, not inside the kernel.** A process in state `D`, waiting inside a kernel call, can't handle anything until that call returns. KILL is marked pending and acts as soon as it does. That's why a process reading from a hung NFS share or a dying USB drive can't be killed until the device answers or times out.

**Handlers are inherited, then reset.** A child made by `fork()` gets a copy of its parent's signal settings. `exec()` resets caught signals to the default, because the handler functions belonged to the old program, but keeps **ignored** signals ignored. That's the trick `nohup` relies on: it sets HUP to ignore and then `exec`s your command, which starts with HUP already ignored. Shells use the same rule to make background jobs in scripts ignore INT and QUIT.

**`kill 0`, `kill -1` and `kill -0`.** The target can be more than one process. `kill 0` signals every process in your own process group, this terminal's shell included. `kill -1` signals every process you're allowed to, which for a normal user means your whole desktop session. `kill -0 PID` sends nothing at all: it only checks whether the process exists and you may signal it, and sets the exit code to say so.

**PID 1 is protected.** The kernel delivers to PID 1 only the signals it has installed handlers for. systemd uses that: it treats some signals as commands, such as SIGTERM to re-execute itself and SIGRTMIN+4 to power off. Everything else sent to PID 1, KILL included, is dropped.

**Real-time signals.** 34 to 64 (`SIGRTMIN` to `SIGRTMAX`) have no fixed meaning. Programs agree on them privately, and unlike the classic signals, several of the same one can queue up instead of merging into one.
