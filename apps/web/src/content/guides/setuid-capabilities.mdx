    reality: "Two reasons it doesn't. Setuid gives the file owner's rights, so it would have to be owned by root. And Linux ignores setuid on scripts entirely: a setuid script run by another user still ran as that user. Use a sudoers rule for the one command instead."
  - myth: "The sticky bit keeps a program in memory."
    reality: "That was its meaning on old Unix systems. Linux ignores it on files. On a folder it means only a file's owner (or the folder's owner, or root) can delete or rename it, which is what protects `/tmp`."
  - myth: "A program either has root's power or it doesn't."
    reality: "Root's power is split into about 40 capabilities: bind low ports, send raw packets, override file permissions, load modules, and so on. A program can hold just the one it needs. `ping` holds only `cap_net_raw`."

## The mental model

The [nine rwx bits](/g/permissions-model) answer "may this process read, write or run this file?". Three more bits change *how* something runs or who may delete things:

| Bit | Octal | On a program | On a folder | `ls -l` shows |
|---|---|---|---|---|
| setuid | 4000 | Runs with the **file owner's** user ID | (ignored) | `s` in the owner's `x` |
| setgid | 2000 | Runs with the **file's group** | New entries get the folder's group | `s` in the group's `x` |
| sticky | 1000 | (ignored) | Only an entry's owner may delete or rename it | `t` in others' `x` |

The letter is lowercase when the `x` underneath is also set, and uppercase (`S`, `T`) when it isn't, which usually means a mistake: `-rwSr--r--` is setuid on a file nobody can run.

Setuid is how an ordinary user can change their own password. `/etc/shadow` is writable only by root, yet `passwd` writes to it. The program is owned by root and setuid, so for the length of that one program you act as root, and the program itself makes sure you only change your own entry:

That's also all [sudo](/g/how-sudo-works) is: a setuid-root program with a policy file. The cost is that every setuid program is a door into root: a bug in one is a way in. So distributions keep the list short, and newer programs use **capabilities**, which hand out one slice of root's power instead of all of it.

## Under the hood

**The kernel ignores setuid on scripts.** For a script, the kernel starts the interpreter from the `#!` line, and it won't apply the script's setuid bit to that interpreter: the gap between checking the file and the interpreter opening it again would be easy to exploit. A setuid `#!/bin/sh` script owned by jd, run by `nobody`, printed plain `uid=65534(nobody)`. Only compiled programs get it.

**The bit doesn't survive changes.** Changing a setuid file's owner or group clears the bit, and so does writing to it. Both happened on the test machine: a `chown jd:jd` by jd on jd's own setuid file, and an append with `>>`, each left `-rwxr-xr-x`. That stops someone from editing a setuid program into something else and keeping its powers.

**Filesystems can switch it off.** A filesystem mounted `nosuid` ignores setuid and setgid bits. `/run` and `/dev/shm` are mounted that way, and so are USB sticks the desktop mounts for you. [Mounts and block devices](/g/mounts-devices) has the other mount options.

**setgid in practice.** `crontab` is setgid `crontab`, and `/var/spool/cron/crontabs` is `1730 root:crontab`: the group may add files but not list them, and the sticky bit stops anyone deleting someone else's. So `crontab -e` can save your file there without root, and can't touch anyone else's. On folders, setgid is the classic way to share: `chgrp team /srv/shared; chmod 2775 /srv/shared`, and every new file inside belongs to `team`. Ubuntu does this for `/var/mail` (group `mail`) and `/var/local` (group `staff`).

**The sticky bit and `/tmp`.** Without it, anyone who can write to `/tmp` could delete or replace anyone else's files there. With it, `rm` of a root-owned file in `/tmp` failed for jd with `Operation not permitted`, although `/tmp` is `rwxrwxrwx`. Ubuntu adds `fs.protected_symlinks`, `fs.protected_hardlinks` and `fs.protected_regular` on top, which stop tricks with links and files that other users leave in sticky folders ([inodes and links](/g/inodes-links)).

**Capabilities.** Root's power is split into 41 named capabilities on this kernel, such as:

- `cap_net_bind_service`: listen on ports below 1024
- `cap_net_raw`: raw sockets, as `ping` needs
- `cap_dac_override`: ignore file permission bits
- `cap_sys_admin`: a large catch-all for mounting and much else
- `cap_kill`: signal any process

A root process normally has all of them; a normal user's processes have none. Each process has several sets: **permitted** (what it may use), **effective** (what is switched on), **bounding** (the ceiling for anything it starts), plus **inheritable** and **ambient** (what passes to programs it runs). `/proc/<PID>/status` shows them as masks; `capsh --decode` names them.

**File capabilities.** `setcap cap_net_raw=ep /usr/bin/ping` stores capabilities in an extended attribute of the file, and the program gets them when it starts, much like setuid but narrower. `getcap` shows them. Ubuntu relies on this because its `net.ipv4.ping_group_range` is `1 0`, which turns off the unprivileged ICMP sockets ping could otherwise use. Distributions that set that range wide, such as Fedora, run ping with no capability at all.

**Low ports without root.** A web server on port 80 needs `cap_net_bind_service`. Rather than running it as root, give a systemd service `AmbientCapabilities=CAP_NET_BIND_SERVICE` and `User=` a normal account. `sudo setcap cap_net_bind_service=+ep $(which node)` also works, but then every script any user runs with that `node` can bind low ports. [Ports and sockets](/g/ports-sockets) explains the rule itself.

**Auditing.** `find / -xdev -perm /6000 -type f` lists setuid and setgid files on the root filesystem, and `getcap -r /` lists capabilities. A setuid file in a home folder or in `/tmp` is a red flag. Never set the bit on a shell, an interpreter or an editor: `chmod u+s /usr/bin/python3` would let anyone run anything as root.
