## The short version

Linus Torvalds' kernel on its own doesn't do anything you could use: it needs a C library, a shell, commands, an init process to start everything else, and some way to install and update programs. In 1991 you assembled those yourself from separate downloads. Within a year people started packaging them together, compiled to work with each other and installable from a set of floppy disks. Those bundles are distributions.

A distribution is more than a pile of software. It's a set of choices: which versions of thousands of programs to ship, how to configure them, which init system and package format to use, how often to release and how long to support each release. Those choices, more than the software itself, are what make Debian different from Fedora or Arch.

Because all of the software is free to copy and change, anyone who disagrees with those choices can make their own distribution. Hundreds of people have. But building and maintaining tens of thousands of packages is a huge job, so most new distributions start from an existing one and change only what they care about. That is why there are hundreds of distributions and only a handful of families.

## Upstream and downstream

A distribution mostly doesn't write the software it ships. GNU writes coreutils, the GNOME project writes GNOME, Mozilla writes Firefox. Those projects are **upstream**. The distribution takes their releases, builds them, and passes the result **downstream** to its users. Distributions can be upstream of each other too: Debian is upstream of Ubuntu, which is upstream of Linux Mint.

Packagers sit in between. They write the build recipe, choose compile options, split the program into packages (`libfoo`, `libfoo-dev`), add patches that fit it to the distribution, and fix bugs, ideally by sending the fix upstream so everyone gets it. When you file a bug, it matters which side it belongs to: a crash in GNOME itself goes upstream, a missing dependency in Ubuntu's package goes to Ubuntu.

The Red Hat family shows the chain clearly. Red Hat describes Fedora as the upstream where future RHEL versions start, CentOS Stream as the place the next RHEL minor version is developed in the open, and RHEL as the product built from it.

## Release models

How often a distribution changes is its most important choice for most users:

| Model | What it means | Examples | Good for |
|---|---|---|---|
| **Fixed release** | A set of versions is frozen, tested together and released. Within a release, only fixes go in. | Debian stable, Fedora, Ubuntu | Predictable systems; you choose when to upgrade |
| **Long-term support (LTS)** | A fixed release that gets security fixes for years, often five or ten. | RHEL, Ubuntu LTS, SUSE Linux Enterprise, Rocky, Alma | Servers and anything that must not change under you |
| **Rolling release** | No versions: packages are updated as upstream releases them, continuously. | Arch, openSUSE Tumbleweed, Void, Debian unstable | The newest software, at the cost of more frequent change |

Debian runs all three at once: stable, the frozen release; testing, where the next stable is assembled; and unstable, which rolls. Ubuntu introduced the term LTS in 2006, when it decided every fourth release, one every two years, would get long-term support.

A fixed release still needs fixes, which is where **backports** come in. A distribution that ships version 2.4 of a program for five years can't just jump to 2.9 when a security hole is found, because 2.9 might change behaviour people depend on. So its maintainers take the fix from upstream and apply it to 2.4. That is why a version number from a stable distribution, like `openssl 3.0.13-0ubuntu3.4`, can be older than upstream's latest and still not be vulnerable: the suffix after the upstream version counts the distribution's own changes.

## Why are there so many?

Partly because there can be. The GPL and similar licences let anyone copy, change and redistribute everything, so a distribution is never anyone's to control: if you disagree with one, you're free to make your own. But "can" doesn't explain why people bother. The reasons that recur:

- **Different goals.** A server wants nothing to change for ten years; a developer wants this month's compiler; a security tester wants hundreds of specialist tools ready to use; a Raspberry Pi needs firmware a PC doesn't. No single set of choices fits all of these, so Kali, RHEL, Fedora and Raspberry Pi OS make different ones.
- **Different values.** Debian has a social contract and its own test for what counts as free software, and keeps non-free firmware in a separate section. Some distributions include only software the FSF approves; others ship proprietary drivers by default because users want hardware to work.
- **Different ideas about how a system should work.** Gentoo compiles everything from source to the owner's settings. NixOS describes a whole machine in one file and can roll it back. Alpine replaces glibc and GNU tools with musl and BusyBox to stay tiny. Void avoids systemd. Each is an argument about design that could only be made by building a distribution.
- **Disagreements and changes of course.** Ubuntu began in 2004 as Debian with a fixed six-month schedule and a company behind it. When Red Hat moved CentOS to CentOS Stream in December 2020, CentOS's original founder started Rocky Linux and another group started AlmaLinux, so people relying on a free RHEL rebuild had one again.
- **A friendlier front end.** Many derivatives keep almost everything from their parent and change the parts a new user sees: an installer, a desktop, a theme, preinstalled codecs. Linux Mint, elementary OS, Zorin OS, Manjaro and EndeavourOS are mostly this.
- **Companies and hardware.** System76 makes Pop!_OS for its own computers, Valve makes SteamOS for the Steam Deck, and Google builds ChromeOS. Each wants control over the whole system it ships.

The cost of starting from scratch keeps the families few. A distribution like Debian maintains tens of thousands of source packages with hundreds of volunteers, plus build servers for many architectures and a security team. A derivative reuses all of that and maintains only its differences, which is why so many distributions are "based on Ubuntu" or "based on Arch". Fully independent distributions, like Void, are rare enough that they say so on their front page.

The overlap also means the differences are smaller than the number of names suggests. Two distributions in the same family share packages, package format, repositories (often directly) and documentation. Moving between Ubuntu and Linux Mint is a change of desktop; moving from Ubuntu to Fedora is a change of package manager and some paths; the commands, the kernel and almost every program are the same.

## Why it matters today

- **Instructions online are written for a family.** "Run `sudo apt install`" means Debian or Ubuntu; `dnf` means Fedora or RHEL; `pacman` means Arch. Knowing your family tells you which answers apply. `cat /etc/os-release` says which distribution you're on and, in `ID_LIKE`, which it's based on.
- **Packages come from your distribution.** That's why [installing a .deb](/s/install-deb) from a website can break things, and why [what a package is](/g/what-is-a-package) matters: the distribution has already matched every package's libraries to the rest of the system. Formats like Flatpak and Snap, in the [app formats guide](/g/app-formats), exist to ship one build to every distribution.
- **Version numbers in a stable release look old on purpose.** Backports keep them safe; check the distribution's security tracker, not upstream's latest version.
- **Choosing a distribution is mostly choosing a release model and a family.** The next chapter compares the families.
