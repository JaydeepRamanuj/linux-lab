Unmerge a Branch with Wrong Code

“A feature was merged into main but the code is broken or unstable — safely undo it without rewriting shared history.”

bolt Primary Recovery Action Revert parent 1
$ git revert -m 1
warning
Caution Required • Future Re-merges

After reverting a merge, simply merging the repaired feature branch later will result in an empty commit. Git remembers the commits were already accepted! To re-merge later, you must first revert the revert, or cherry-pick the revised commits.

troubleshoot

The Situation

A pull request was approved and integrated into main. CI pipelines or QA tests detected a critical regression. Because team members have likely already pulled or branched off main, resetting with git reset --hard would break everyone’s local clone.

schema Repository Commit Topology
BEFORE RESOLUTION Broken Main
(main) A — B — M [HEAD] (Bad merge)
AFTER RESOLUTION History Preserved
(main) A — B — M — M' [HEAD] (Inverts M)
psychology How git revert -m 1 Works expand_more

A merge commit has two (or more) parent commits. Git does not automatically know which side of the merge represents the mainline you want to preserve and which branch brought in the offending changes.

  • -m 1 (Parent 1): Specifies the branch that was merged into (usually main). Git computes a patch that returns your codebase to Parent 1's exact tree state.
  • -m 2 (Parent 2): Specifies the branch that was merged in (e.g., feature/checkout). Reverting against Parent 2 would discard main's commits instead!

How to Avoid This in the Future

check_circle
Mandate Staging Verification

Deploy pull requests to an ephemeral preview or staging environment before approving the merge to main.

check_circle
Decouple with Feature Flags

Wrap volatile features in remote config or feature toggles so you can disable regressions in seconds without needing Git reverts.
